# Test Strategy（TDD 適用判断）

実装計画を作成するとき、**ステップごと**に「テストを先に書くか（TDD）／実装後に書くか／書かないか」を決めるための基準。

## このドキュメントの責務

| ドキュメント | 定めること |
|---|---|
| **本ドキュメント** | テストを**いつ**書くか（実装より先か・後か・書かないか） |
| `.claude/skills/testing-backend/SKILL.md` | Domain / Application 層のテストを**何を・どう**書くか（種別・規約・パターン） |
| `.claude/skills/create-e2e-test/SKILL.md` | E2E テストを**何を・どう**書くか |

種別（単体／統合／不要）の定義は `testing-backend` の表が正であり、本ドキュメントはそれを上書きしない。

## 判断表

| 実装対象 | テスト種別 | 書く順序 |
|---|---|---|
| Domain 層 — Value Object / Entity | 単体（インメモリ） | **TDD** |
| Domain 層 — Domain Service | 統合（実DB） | **TDD** |
| Application 層 — Command / Query | 統合（実DB） | **TDD** |
| バグ修正（再現手順が特定できている） | 種別は対象レイヤーに従う | **TDD**（再現テストを先に書き RED を確認する） |
| Infrastructure 層 — Prisma リポジトリ / QueryService | テスト不要 | — （Application 層テストが間接的にカバーする） |
| Prisma スキーマ変更 / マイグレーション | テスト不要 | — |
| Presentation 層 — Server Action / 画面 / コンポーネント | E2E | **実装後**（画面が動く前に E2E は書けない） |
| seed / 設定ファイル / ドキュメント | テスト不要 | — |

## 判断の考え方

表で判断がつかない実装に出会ったら、次の問いに答える。

**TDD が効くのは、期待する振る舞いを実装前に言い切れるとき。** 「社員コードが重複していたら ValidationError」は、実装を一行も書かずにテストとして表現できる。だから先に書く価値がある — RED が「まだ無い」ことを証明し、GREEN が「できた」ことを証明する。

**TDD が空回りするのは、正解が実装の結果として初めて分かるとき。** マイグレーションの正しさは「migrate が通り、既存データが壊れないこと」であって、事前に書いたテストが証明できるものではない。画面のテストも同様で、DOM 構造やセレクタが決まる前に E2E は書けない。ここで無理に先にテストを書くと、実装の**形**をなぞるだけのテスト（リファクタで壊れ、バグは見逃す）が生まれる。

迷った場合の既定は **TDD**。判断を誤ってテストを後に回すコストの方が、先に書いて空振りするコストより高い。

## 計画ファイルへの記載

判断結果は計画ファイルの各ステップに `テスト戦略:` として明記する（`docs/claude-plans/PLAN_TEMPLATE.md` 参照）。値は次の 3 つのいずれか。

- `TDD` — red-green-refactor で進める。テストを先に書き、RED を確認してから実装する
- `実装後テスト` — 実装してからテストを書く（主に E2E）
- `テスト不要` — テストを書かない。理由を併記する（例: `テスト不要（マイグレーション）`）

DDD の層を縦断する Issue では、ステップごとに戦略が変わるのが普通である。Issue 全体で一律に決めない。
