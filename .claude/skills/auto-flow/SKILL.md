# プロンプト内容

あなたは開発フロー全体のオーケストレータです。
以下の 5 フェーズを順に実行してください。

```
Phase 1  grill-with-docs   [メイン文脈]      ← ユーザーが関与（設計判断）
─────────── ここから自動 ───────────
Phase 2  save-plan         [メイン文脈]      会話 → 計画ファイル
Phase 3  auto-tdd          [独立エージェント] 計画ファイル → 実装 + コミット
Phase 4  create-pr         [独立エージェント] git → PR
Phase 5  auto-review-fix   [メイン文脈]      PR → レビュー修正ループ
─────────────────────────────────────
Phase 6  残課題を提示                        ← ユーザーが関与（残課題チェック）
```

## このフローの原則（最重要）

- **ユーザーが関与するのは Phase 1（設計判断）と Phase 6（残課題チェック）だけ**。Phase 2〜5 の途中で確認を求めない。
- **Phase 1 → Phase 2 の移行はユーザーの明示的なゴーサインを必須とする**（後述）。勝手に実装を始めない。
- **フェーズが失敗したら、そこで止める**。後続フェーズを強行しない。各フェーズの成果物（計画ファイル / コミット / PR）はすべて永続化されるため、**失敗したフェーズから個別スキル（`/save-plan` `/auto-tdd` `/create-pr` `/auto-review-fix`）で手動再開できる**。再開方法を必ず報告に含めること。
- **各フェーズは対応するスキルに委譲する。オーケストレータが実装やPR作成を自分でやらない。**

---

## Phase 0: 前提チェック

```bash
git branch --show-current
git status --short
```

**ブロッカー（該当したら即終了）:**

- ブランチが `develop` / `main` / `master` の場合 → 終了する。理由: 作業ブランチ以外で実装・push させないため。
  → `/dev-worktree` で作業用 worktree を作るよう案内する。
- ブランチ名から Issue 番号（`issue-{N}`）を抽出できない場合 → 終了する。
  → 後続の全スキル（save-plan / auto-tdd / create-pr / auto-review-fix）がブランチ名から Issue 番号を検出する設計のため。

**警告（報告して続行判断を仰ぐ）:**

- 未コミットの変更がある場合 → 内容を提示し、コミットするか退避するかをユーザーに確認する。

Issue 情報を取得しておく（Phase 1 の材料にする）:

```bash
gh issue view {N} --json title,body,labels
```

---

## Phase 1: 設計対話（ユーザーが関与）

`Skill` ツールで `grill-with-docs` を起動する（`skill: grill-with-docs`、`args: "#{N} {Issue タイトル}"`）。

- このフェーズは**メイン文脈で実行する**（ユーザーとの対話そのものであるため）
- `grill-with-docs` の規約に従い、**質問は1つずつ**投げて必ずユーザーの返答を待つ。返答を勝手に想像・代筆しない。
- 用語が固まったら `CONTEXT.md` を、ADR に値する判断が出たら（ユーザーが起票を判断したら）ADR をその場で更新する

### Phase 1 → Phase 2 の移行条件（厳守）

**未解決の設計分岐が尽きたら、次の確認を1回だけ出して停止し、ユーザーの返答を待つ:**

```
設計が固まりました。ここから自動フェーズに入ります。

  Phase 2  計画をファイルに保存
  Phase 3  実装（計画のテスト戦略に従う）
  Phase 4  PR 作成
  Phase 5  自動レビュー＆修正ループ

進めてよろしいですか？（続行 / まだ詰めたい点がある）
```

- **ユーザーが明示的にゴーサインを出すまで Phase 2 に進んではいけない。**
- ユーザーがさらに論点を出したら Phase 1 の対話に戻る。
- 理由: 設計はこのフローで唯一ユーザーが握るべき部分であり、合意の宣言をモデルが代行してはならないため。

---

## Phase 2: 計画の保存（メイン文脈）

`Skill` ツールで `save-plan` を起動する（`skill: save-plan`、`args: "#{N}"`）。

- **このフェーズはメイン文脈で実行する。サブエージェントに委譲してはいけない。**
  理由: `save-plan` の入力は「Phase 1 の会話そのもの」であり、合意内容はまだファイルのどこにも存在しない。fork したサブエージェントは会話履歴を引き継がないため、切り出すと合意が失われる。
- 返却された**計画ファイルのパス**を記録し、Phase 3 に引き渡す。

**失敗時**: 計画ファイルが作られなかったら Phase 3 に進まない（実装の根拠が無いため）。理由を報告して終了する。

---

## Phase 3: 実装（独立エージェント）

`Skill` ツールで `auto-tdd` を起動する（`skill: auto-tdd`、`args: "#{N}"`）。

- `auto-tdd` は `context: fork` により**独立したサブエージェントとして実行される**
- 会話履歴は渡らない。**計画ファイルが唯一の入力**であり、それで足りるように Phase 2 が書き切っている
- 返却値から「状態 / test の緑赤 / 逸脱の有無」を読み取る

**分岐:**

| auto-tdd の状態 | 次の行動 |
|----------------|---------|
| 完了（test 緑） | Phase 4 へ（通常 PR） |
| テスト赤で停止 | Phase 4 へ（**draft PR**）。Phase 5 はスキップして Phase 6 で報告 |
| 実装不能で停止 | Phase 4 へ（**draft PR**）。Phase 5 はスキップして Phase 6 で報告 |

テストが赤のまま自動レビュー修正ループ（Phase 5）に入れないこと。レビューの前提が崩れるため。

---

## Phase 4: PR 作成（独立エージェント）

`Skill` ツールで `create-pr` を起動する（`skill: create-pr`、`args: "#{N}"`）。

- `create-pr` は `context: fork` により**独立したサブエージェントとして実行される**
- 会話履歴は渡らないが問題ない。`create-pr` は計画ファイル・逸脱記録・git ログから PR body を組み立てる設計のため
- **Phase 3 が「テスト赤」「実装不能」だった場合**は `args: "--draft #{N}"` で draft PR を作成する
- 返却値から **PR 番号と URL** を取得する

**失敗時**: PR が作られなかったら Phase 5 に進まない。理由を報告して終了する。

---

## Phase 5: 自動レビュー＆修正（メイン文脈）

`Skill` ツールで `auto-review-fix` を起動する（`skill: auto-review-fix`、`args: "{PR番号}"`）。

- **このフェーズはメイン文脈で実行する。**
  理由: (1) `auto-review-fix` は内部でさらに `Skill(code-review)` を起動する多段構成であること、(2) 直後の Phase 6 でユーザーが残課題をチェックするため、文脈をメインに残しておく方がそのまま議論を継続できること。
- `auto-review-fix` の規約（バケツ①②③を修正・④は残課題として報告のみ・最大3ラウンド）に従う
- Phase 3 が draft PR だった場合はこのフェーズを**スキップ**する

---

## Phase 6: 最終報告（ユーザーが関与）

ユーザーが**残課題をチェックする**ためのフェーズ。判断材料を漏れなく提示する。

```
✅ 開発フロー完了

📋 Issue: #{N} {title}
🔗 PR: {PR URL}
📄 計画: docs/claude-plans/issue-{N}/{file}.md
🌿 Branch: {ブランチ名}

## 自動で解消したもの
- [{バケツ}] {file:line} {問題} → {対応内容}

## judge が却下したもの（計画準拠・誤検知・スコープ外）
- {file:line} {問題} → {却下理由}

## 🔍 残課題（あなたの判断が必要）
- {file:line} {問題} → 理由: {テスト不足 / 命名・責務 / cleanup基準未達 / 未解消の①②}

## 状態
- test: 緑 / 赤（{失敗したテスト}）
- 逸脱: あり（PR の「計画からの逸脱」参照） / なし
- レビューラウンド: {n}/3（終了理由: {収束 / 上限到達 / no-progress}）
```

- **残課題（バケツ④）を必ず明示する**。ここがユーザーの関与ポイントであり、フローの成果物。
- テストが赤・未解消の指摘が残っている場合は**隠さず報告する**。
- 途中フェーズで停止した場合は、**どのフェーズで落ちたか**と**再開コマンド**（例: `/auto-tdd #{N}`）を提示する。
