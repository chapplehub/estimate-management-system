# プロンプト内容

あなたは PR の自己修正ループを回す自動レビュー＆修正エージェントです。
`$ARGUMENTS`（`[PR番号] [深さ]` / いずれも省略可）を入力として、**`/code-review` → 評価（指摘の種類で仕分け）→ バケツ別に修正 → push → 再レビュー** を収束するまで自動で繰り返してください。

**判定の中核**: severity（Critical/High/Medium/Low）による足切りは行わない。代わりに各指摘を**4 つのバケツ**に仕分け、バケツごとに対応方針を変える。severity は報告・参考ラベルとして併記するだけで、採否・終了判定には一切使わない。

| バケツ | 内容 | 対応 |
|---|---|---|
| **① correctness bug** | 間違った出力 / クラッシュを起こすバグ | judge が本物と確認したら**直す**（severity 不問） |
| **② 方針・アーキ違反** | **DDD 層違反 / 楽観ロック欠落 / NULL 方針違反**（固定 3 項目） | 本物と確認したら**常に直す**（cleanup 基準にかけない） |
| **③ cleanup** | reuse / simplification / efficiency / altitude | **③の採用基準を満たせば直す** |
| **④ 残課題** | テスト不足・命名・却下（誤検知/計画準拠/スコープ外）等 | 直さず**報告のみ** |

- **多重該当時の優先順位: ② > ① > ③ > ④**。1 つの指摘が複数に当たり得る場合は左を優先する（例: バグ修正が同時に簡素化でもある → ①。重複ロジックが実は NULL 方針違反 → ②）。

## 重要な前提条件

- **対象ブランチの worktree 内から実行する**（feat/fix 等の作業ブランチ）。`develop` / `main` / `master` では実行しない。
- 自動 push は **作業ブランチのみ**。`pre-bash-branch-safety.sh` フックと整合させる。
- ユーザーへの逐次確認は行わない（ループ全体を自動実行する）が、**終了条件に到達したら必ず止まる**。
- **レビューは必ず組み込みの `code-review` スキルを使う**（`Skill` ツール経由。`skill: code-review` で起動する）。独自レビューで代替しない。

## Phase 0: 入力解析・対象 PR の特定・安全確認

### 0.1 入力解析（PR番号と深さ）

`$ARGUMENTS` を空白区切りで解析する。

- **深さ**: `low` / `medium` / `high` / `xhigh` / `max` のいずれかのトークンがあればそれを採用。なければ既定 **`medium`**。
  - これは `/code-review {深さ}` の effort level に渡す。深いほど不確実な指摘も拾う代わりに時間がかかる。
- **PR番号**: `#123` / `123` 形式のトークンがあればそれを使う。省略時は 0.2 で特定する。

例: `/auto-review-fix #123 high` → PR 123 を深さ high で。`/auto-review-fix xhigh` → 現在ブランチの PR を深さ xhigh で。

### 0.2 PR 番号の特定（省略時）

```bash
git rev-parse --abbrev-ref HEAD
gh pr view --json number,title,headRefName,state
```

- PR が存在しない / クローズ済みの場合はエラーとして理由を返し終了する。

### 0.3 Issue 番号と計画ファイルの特定

- ブランチ名（`feat/issue-123` 等）から Issue 番号を抽出する。
- 計画ファイルの場所を控える（評価ステージで読む）:

```bash
ls docs/claude-plans/issue-{番号}/
```

- `plan.md` または自動命名の `*.md`、加えて `deviations.md`（あれば）。**計画ファイルが見つからない場合はその旨を記録し、評価は実装意図の推測に頼る**ことを明記する。

### 0.4 安全確認（ブロッカー）

- ブランチが `develop` / `main` / `master` の場合は **即終了**する。理由: 作業ブランチ以外への自動 push を禁止するため。
- worktree がクリーンでない（未コミットの変更がある）場合は一旦コミット or 報告して終了する。

## ループ本体（最大 3 ラウンド）

以下の Phase 1 → 1.5 → 2〜5 を、**終了条件に達するまで**繰り返す。ラウンド番号を `R`（1 始まり）とする。

### 終了条件（いずれか満たしたら停止）

終了判定のドライバは **採用された ①correctness ＋ ②方針違反の件数**（以下「採用①②」）。③cleanup は機会主義的な掃除なので**終了判定に含めない**（別キャップも設けない）。

1. **収束**: 評価で**採用①②が 0 件** → 成功として Phase 6 へ。ただし今ラウンドに採用③（cleanup）があれば、**それだけは Phase 4 で処理してから** Phase 6 へ。
2. **回数上限**: `R > 3` → 未収束として Phase 6 へ（残課題を報告）。
3. **no-progress**: 前ラウンドと比べて採用①②の件数が**増えている**（増加） → 発散とみなし Phase 6 へ（人間の判断が必要と報告）。

---

### Phase 1: レビュー（組み込み `/code-review` を確実に使う）

**`Skill` ツールで `code-review` スキルを起動する（`skill: code-review`、`args: {深さ} {base}...HEAD`）。** ここはメイン文脈で実行する（`Skill` ツールはサブエージェント内では起動できないため）。

- **/code-review は「検出専用」として使う**（PR への記録は Phase 1.5 に一本化する）。`--comment` は **付けない**: インライン投稿はアンカー不能分が黙って落ちる不確実な経路であり、Phase 1.5 のトップレベル投稿と重複するため。
- **レビュー対象を PR の ref 範囲に固定する（`{base}...HEAD`）**: `{base}` は PR のベースブランチ（通常 `develop`。Phase 0.2 の `gh pr view --json baseRefName` で確認し、`develop` でなければそれを使う）。
  - 理由: `/code-review` の既定スコープは「upstream より先行しているコミット＋未コミット変更」であり、push 直後やトラッキング設定次第で **レビューした diff が PR の diff と食い違う**。ref 範囲形式は upstream 設定に依らず「その PR が持つコミット差分」をレビューするため、スコープが PR と一致する。未コミット変更（PR に無い）を拾う事故も防ぐ。
- `--fix` は **付けない**（評価前に勝手に直させない）。修正は評価（judge）を通ったバケツ①②③だけに限定する。
- **findings はセッション内に必ず表示される**ので、それを丸ごと控えて Phase 1.5・Phase 2 へ渡す。判定と記録の一次情報は **この セッション findings**。

### Phase 1.5: findings の記録（トップレベル投稿）と Phase 2 ゲート

**生 findings を auto-review-fix 側（メイン文脈）が決定的に PR へ記録する。** これを通してからでないと Phase 2 に進まない。

1. **findings 0 件の判定（収束ゲート）**: Phase 1 のセッション findings が空（`/code-review` が指摘ゼロ）なら「収束」。**Phase 2 に進まず Phase 6 へ**。
2. **findings ≥1 件なら、生 findings をトップレベルコメントとして必ず投稿する**（行アンカー不要なので 100% 残る）:

```bash
gh pr comment {PR番号} --body "$(cat <<'EOF'
## 🔍 /code-review 生レビュー ラウンド {R}（深さ {深さ} / 対象 {base}...HEAD）

Phase 1 の `/code-review` が返した指摘（judge 評価前の一次情報）:

- [severity参考:{severity}] {file:line} {問題}
EOF
)"
```

3. 投稿の成否を確認する（`gh pr comment` の終了コード）。**投稿できなければ Phase 2 に進まない**（原因を記録して停止する）。
4. 投稿できたら、そのセッション findings を持って Phase 2 へ。

> これにより「Phase 1 の結果が PR に載らないまま Phase 2 に進む」が構造的に起きなくなる。PR には「Phase 1.5 の生レビュー（トップレベル）」「Phase 2 の judge 判定」の 2 層が記録として残る。

### Phase 2: 評価（fresh subagent で妥当性を judge）— **鵜呑みにしない**

`/code-review` の結果を**そのまま採用しない**。毎ラウンド新しいサブエージェントを `Agent`（Task）ツールで起動し、**評価者（judge）**として各指摘の妥当性を判定させる。
理由: レビューを出す者と採否を決める者を分離し、誤検知（false positive）の修正・計画と矛盾する修正を防ぐため。各ラウンド起動し直す（文脈を引き継がない）。

**judge は判定のみ。コード修正・ファイル編集・コミットを絶対に行わない**（Edit / Write / git commit を禁止）。judge の責務は「採否と理由を返すこと」だけで、実装には一切触れない。

judge サブエージェントへのプロンプトに以下を**すべて**渡す:

1. **`/code-review` の指摘リスト**（**Phase 1 のセッション findings をそのまま**。Phase 1.5 でトップレベル投稿したものと同一の一次情報。PR のインラインコメントを読み直すのではなく、この findings を判定材料にする）
2. **実装の変更内容**: `git diff {base}...HEAD`
3. **計画ファイルの中身**: `docs/claude-plans/issue-{番号}/*.md`（`deviations.md` 含む。無い場合はその旨）
4. 下記「バケツ分類基準」と「③ cleanup の採用基準」
5. 下記「参考: severity ラベル（報告用）」

#### judge の判定基準（バケツ分類）

各指摘について、まず**却下かどうか**を判断し、採用なら**どのバケツか**を確定して `{バケツ, severity(参考), 採否, 理由}` を返す。

**却下**（次のいずれか。バケツ④の一部として報告のみ）:
- **計画準拠**: 指摘は「あるべき」と言うが、**計画ファイルで意図的にそう設計している**（＝計画が正、指摘が文脈無視）。
- **誤検知**: コードを誤読している / 実際には成立しない経路。
- **スコープ外**: この PR の責務外（別 Issue にすべき）。

**採用時のバケツ分類**（**多重該当は ② > ① > ③ > ④ の優先順位**で決める）:

- **② 方針・アーキ違反**（最優先で拾う。本物なら**常に直す**）— 次の**固定 3 項目**のいずれかに該当するもの。**この 3 項目がバケツ②の正本**:
  1. **DDD 層違反**: Domain 層が infrastructure / application / presentation に依存。Domain 層が Prisma / Next.js / 外部ライブラリを import している。Application 層が repository の具象実装に依存（interface でない）。
  2. **楽観ロック欠落**: 更新系で version を伴わない書き込み（特に Employee は外部認証副作用ゆえ version 付き書き込みを先頭に）。
  3. **NULL 方針違反**: kawasima デシジョンツリー準拠の NULL 排除方針に反する nullable 追加。
  - 上記 3 項目**以外**の ADR 違反（集約境界・Money パターン等）はバケツ②には入れない。③または④で扱う。
- **① correctness bug**（本物なら**直す**、severity 不問）— 間違った出力 / クラッシュ / データ不整合 / 未処理の例外パスなど、`/code-review` が correctness として挙げた実害バグ。judge は「本当にバグか」を確認する。
- **③ cleanup**（**下記「③ の採用基準」を満たせば直す**）— `/code-review` が reuse / simplification / efficiency / altitude として挙げた掃除系。基準未達なら④へ落とす。
- **④ 残課題**（直さず報告のみ）— ①②③のいずれでもないもの（テスト不足・命名/責務の乱れ 等）、③の基準未達、および上記の却下分。

##### ③ cleanup の採用基準（**次の 3 つをすべて満たす時のみ採用**）

1. **挙動不変**: 観測可能な振る舞いを変えない純粋なリファクタ/最適化。既存テストが緑のまま通る。挙動が変わり得るなら ④。
2. **設計判断が不要**: どこに置くか・どう抽象化するか・責務をどう分けるかで迷う余地がない。判断が要る時点で ④。
3. **局所的**: 少数ファイルに閉じ、レイヤ / 集約をまたぐ波及や、公開シグネチャ変更による呼び出し側の一斉修正を伴わない。

**抽出の可否**:
- **同一ファイル内の private 関数抽出**は可（最も安全なリファクタ）。
- **public 共通関数の抽出**は、次を**すべて**満たす時のみ可。1 つでも怪しければ ④:
  - **3 か所以上**で**意味的に同一**のロジック（構文が似ているだけ・意図が違うものは対象外）。
  - **完全に無状態**: 抽出関数は素のデータ入力だけを取り、常に同じことをする。**挙動を選ぶ引数（flag / mode / boolean）が 1 つでも要るなら抽出しない → ④**（フラグ引数で内部分岐を作る"共通化もどき"を禁止）。
  - **置き場所が既存の明白なホームに一意に定まる**: 3 か所が**同一レイヤ**にあり、そのレイヤに既にこの種のロジックを置く場所（既存 util / domain-policy 等）が存在する。新規共有モジュールの新設やレイヤをまたぐ配置が要るなら → 設計判断ありとみなし ④。
- 旧基準の「共通化による純減（行数減）」は**必須ゲートから外す**（efficiency/altitude は行数が減らないことがあるため）。純減は共通化時の十分条件の一例に留める。
- **迷ったら直さない**を徹底する。③採用は終了判定に含めない（詳細は Phase 3）。

judge の出力形式: 指摘ごとに `{バケツ(①/②/③/④), severity(参考), file:line, 問題, 採否, 理由}` の構造化リスト。③採用には採用根拠（挙動不変・置き場所・3か所同一 等）を理由に明記する。

#### judge 判定を PR に投稿（必須）

judge の結果を受け取ったら、メイン文脈から **PR に judge 判定を残す**:

```bash
gh pr comment {PR番号} --body "$(cat <<'EOF'
## ⚖️ judge 評価 ラウンド {R}（/code-review {深さ} の指摘を種類で再評価）

### 採用（修正対象）
- [{バケツ} / severity参考:{severity}] {file:line} {問題} → 理由: {採用根拠}

### 却下・残課題（修正しない）
- [④] {file:line} {問題} → 理由: {計画準拠 / 誤検知 / スコープ外 / ③基準未達 / テスト不足・命名等}
EOF
)"
```

これにより「`/code-review` の生指摘（Phase 1 の `--comment`）」と「judge の採否判断」の**両方が PR に記録**として残る。

#### 参考: severity ラベル（報告用）

**severity は採否・終了判定には使わない**。PR コメントやサマリで指摘の目安の大きさを伝えるための**参考ラベル**にすぎない。judge は採用した指摘に下記の目安で severity を併記する（迷えば付けなくてよい）。

- **Critical**: ビルド/テストが壊れる、データ破壊、認証・認可の欠落。
- **High**: DDD 層違反 / 楽観ロック欠落 / NULL 方針違反（= バケツ② の 3 項目。**正本はバケツ② の定義**）、明確なバグ・データ不整合・未処理の例外パス（= バケツ①）。
- **Medium**: テスト不足、命名/責務の乱れ、軽微な設計の歪み。
- **Low**: スタイル、コメント、好みの範囲。

> 注: バケツ② の 3 項目は severity ではなく**バケツ分類の正本**（前掲「judge の判定基準」）が定義元。ここは severity ラベル付けの参考に留める。

### Phase 3: 振り分け

今ラウンドの修正対象は採用された **①correctness ／ ②方針違反 ／ ③cleanup** の 3 バケツ:

1. **① correctness bug** — judge が本物と確認したバグ。
2. **② 方針・アーキ違反** — DDD 層違反 / 楽観ロック欠落 / NULL 方針違反。
3. **③ cleanup** — ③の採用基準（挙動不変・設計判断不要・局所的、＋抽出ルール）を満たした掃除。

- **収束判定・no-progress 判定は「採用①②」の件数だけ**で行う（③は判定に含めない）。理由: ③は機会主義的な掃除であり、ループの継続根拠にしないため。
- 採用①②が 0 件なら「収束」。ただし**今ラウンドに採用③があれば、それだけは Phase 4 で処理してから** Phase 6 へ。
- **④残課題**（却下＝計画準拠/誤検知/スコープ外、③基準未達、テスト不足/命名等）はこのループでは修正しない（Phase 6 のサマリに理由付きで残す）。

### Phase 4: 採用バケツの修正（計画ファイルを作ってから着手）

**いきなり修正しない。まず修正計画ファイルを作成してから実装に入る。**

#### 4.1 修正計画ファイルの作成

今ラウンドの修正対象（**採用 ①correctness ／ ②方針違反 ／ ③cleanup**）について、修正方針を計画ファイルへ書き出す。

- 保存先: `docs/claude-plans/issue-{番号}/`
- ファイル名: **ラウンド番号をプレフィックスにする**。ラウンド1なら `r1-`、ラウンド2なら `r2-`。
  - 例: `docs/claude-plans/issue-123/r1-fix-plan.md`
- 記載内容: 対象ごとに `{バケツ, severity(参考), file:line, 問題, 修正方針, 影響範囲, 想定テスト}` を書く。③cleanup は採用根拠（挙動不変・置き場所・3か所同一 等）も併記する。
- DDD 層配置の判断を伴う場合は、その配置理由も計画に明記する（後でコミットボディに転記する）。

#### 4.2 実装

- 計画ファイルに沿って、今ラウンドの修正対象のみを修正する。**DDD 層ルール（CLAUDE.md）を絶対に破らない。**
- **修正順**: **①②（correctness / 方針違反）を先に直して落ち着かせてから、③cleanup を最後に当てる**。③が①②で触った箇所に被る事故を避けるため。
- ③cleanup は実装後に**挙動不変を再確認**する（`pnpm test` が緑のまま／public 抽出なら無状態・置き場所が計画どおりか）。挙動が変わった・基準を満たせなくなった場合は破棄し、④残課題に戻す。
- 意味のあるまとまりごとにコミットする（一括コミットしない）。
  - ①correctness → `fix:` ／ ②方針違反 → 原則 `fix:`（DDD 配置換えなど構造変更主体なら `refactor:`）／ ③cleanup → `refactor:`（統合/共通化）でコミット。計画ファイル自体は `docs:`。
- コミットは `.claude/references/commit-types.md` の type に従う。
- **設計判断を含む場合はコミットボディに理由を記載**（CLAUDE.md のルール）。
- 修正後、テストを実行して緑を確認する:

```bash
pnpm test
pnpm lint
```

- テストが赤のまま push しない。直せない場合は Phase 6 で正直に報告する。

### Phase 5: push と再レビューへ

```bash
git push
```

- 今ラウンドの対応内容を PR にコメントする:

```bash
gh pr comment {PR番号} --body "$(cat <<'EOF'
## 🔁 自動レビュー＆修正 ラウンド {R}（/code-review {深さ}）

### 対応した指摘（採用 ①②③）
- [{バケツ}] {file:line} {問題} → {対応内容}

### 対応しなかった指摘（④残課題・参考）
- {file:line} {問題} → 理由: {計画準拠/誤検知/スコープ外/③基準未達/テスト不足・命名等}

### 次ラウンドで再レビューします
EOF
)"
```

- 採用①②の件数を記録（no-progress 判定に使う。③は数えない）し、`R` を +1 して Phase 1 へ戻る。

---

## Phase 6: 収束サマリ

ループ終了後、結果を PR にコメントする。

```bash
gh pr comment {PR番号} --body "$(cat <<'EOF'
## ✅ 自動レビュー＆修正 完了サマリ（/code-review {深さ}）

- ラウンド数: {実行数} / 上限 3
- 終了理由: {収束 / 上限到達 / no-progress}

### 解消した指摘（①correctness / ②方針違反 / ③cleanup）
- [{バケツ}] {file:line} {問題} → {対応内容}

### 却下した指摘（計画準拠・誤検知・スコープ外）
- {file:line} {問題} → {却下理由}

### 残課題（④・人間の判断が必要）
- {file:line} {問題} → 理由: {③基準未達 / テスト不足 / 命名・責務 / 未解消①②（テストが直せない等）}
EOF
)"
```

- ユーザーへの最終報告では、**自動で解消したもの / judge が却下したもの / 人間の判断に委ねるもの**を明確に分けて返すこと。
- テスト赤・未解消の①②が残った場合は、それを隠さず正直に報告する。
