# CQRS読み取りモデルにおける検索条件の SQL/ドメイン分担

作成日: 2026-07-07

## 概要

状態を列として保存せず、イベント行の存在から毎回導出する設計（ADR-0058）のもとで、一覧画面の検索条件を **SQL（DB）で絞るか、ドメイン（サーバのコード）で絞るか** をどう切り分けるかの原則をまとめる。

結論を一文で言うと:

> **事実（テーブルに保存された値・行の存在）はSQLで絞る。業務規則による写像と、その規則を適用して初めて得られる導出値はドメインで絞る。**

きっかけは #571「見積申請一覧 検索クエリ（SearchEstimateApplications）」の設計議論。「今までSQLで完全に条件を絞ってフロントに返す実装しかしてこなかった」という状態からの学びを整理したもの。

## 背景：状態を列に持たない設計（ADR-0058）

見積申請の状態（申請中／差戻／取下／承認済）は、DBに `status` 列として**存在しない**。存在するのは終端イベント表の**行だけ**:

- `estimate_application_withdrawals`（取下）
- `estimate_step_rejections`（差戻）
- `estimate_step_approvals`（承認）

状態は「どの行が在るか」から毎回導出される（§3.6）:

```
hasWithdrawal      → WITHDRAWN   (最優先)
hasAnyRejection    → REJECTED
allStepsApproved   → APPROVED
それ以外            → PENDING
```

この写像を実装した唯一の関数が `deriveApplicationStatus`（純粋関数）で、**書き込み側（集約 getter `EstimateApplication.applicationStatus`）と読み取り側（クエリ）の両方が同じ1関数を呼ぶ**。

重要な帰結: **状態は列でないため、SQLの `WHERE status = ?` が直接触れない**。だから「状態で絞る」は素直にSQL化できず、SQL/ドメインの分担という論点が生まれる。

## 誤解の解消：「アプリ層」＝サーバであってフロントではない

「SQLで絞らない条件は、フロント（ブラウザ）で絞るのか？ それは遅いのでは？」という懸念は誤解。**絞り込みはすべてサーバ内で完結し、ブラウザには絞り終えた最終結果しか送らない。**

このリポジトリの層構造（presentation / application / infrastructure）は**すべてサーバ内（Next.js のサーバプロセス）**。ブラウザとは別物。

- **PostgreSQL（DBサーバ）**: SQLを実行 ← 不変条件でここが絞る
- **サーバのコード（`PrismaXxxQueryService` 等）**: DBから受け取った候補をメモリで畳み・導出条件で絞る ← 「ドメイン/アプリ層で絞る」はここ
- **ブラウザ**: 絞り終えた DTO 配列を描画するだけ ← **絞り込みは一切しない**

### データフロー

```
ブラウザ ──検索条件──▶ サーバ(Next.js) ──▶ QueryService ──▶ Prisma ──▶ PostgreSQL
                                                                          │
                                          ①不変条件で絞った候補行 ◀──────┘
                                                    │
                        サーバのコードで: 最新申請へ畳む→②導出条件で絞る→ソート→limit
                                                    │
ブラウザ ◀──最終DTO(≤LIST_FETCH_LIMIT件)── サーバ
```

DB→サーバ間はローカル通信で速く、ブラウザへ渡るのは絞り終えた最終結果だけ。従来の「SQLで全部絞る」との違いは **絞る場所がDBかサーバか** だけで、どちらもバックエンド内の話。

### 性能懸念への回答

- 重い絞り込み（見積番号・得意先名・納品先名・有効/無効・「申請or免除あり」）は**全部SQL側**。候補集合はここで十分小さくなる。
- 残った候補（有界＝社内見積の業務量）に対するメモリ絞りはサブミリ秒で、SQLクエリ本体やネットワークに比べ無視できる。

## 切り分けの原則

### 原則1：演算子ではなく「対象が事実か導出値か」

境界を決めるのは演算子（`=`, `<`, `EXISTS`）ではない。**その条件が問う「対象（subject）」が、テーブルに存在する事実か／規則を適用して初めて得られる導出値か**で決まる。

- **SQLで絞る ＝ 対象が「保存された事実」**: 列比較・範囲（`finalTotal >= X`, `createdAt BETWEEN`, `name LIKE`）も、行の存在・件数・結合（`EXISTS`, `NOT EXISTS`）も、DBが物理的に持つ値を問う限りSQL。**EXISTS も「その行が在るか」という事実の質問なのでSQLの領分**（このプロジェクトも `申請 or 免除あり` ＝ `applications: { some: {} }` をSQL側に置いている）。
- **ドメインで絞る ＝ 対象が「規則を適用して初めて出る導出値」**: 状態導出（§3.6 の優先順位つき写像）、畳み込み・代表選択（「最新申請＝attempt最大」「代表バリエーション」）、集約不変条件（「前進バリエーション」「1見積1前進」）。

**核心: 演算子の単純さは無関係。同じ範囲検索でも対象が変われば層が変わる。**

| 条件 | 対象 | 層 | 理由 |
|---|---|---|---|
| 税込合計 ≥ X | `variation.finalTotal`（保存列） | SQL | 事実への不等号 |
| 申請日 が期間内 | **最新**申請の `createdAt` | ドメイン | 「最新」＝畳み込み。対象が導出値 |

「申請日レンジ」は単純な `BETWEEN` に見えて、左辺の「最新申請の日時」が"最新"という規則を通さないと定まらないため、ドメイン側になる。

### 原則2：さらに深い軸「汎用機構か業務規則か（＝持ち主が割れてドリフトするか）」

「導出だからドメイン」は一括りにしすぎ。導出にも濃淡がある。真の軸は **複雑さではなく「単一の持ち主を持ち、業務都合で独立に変わりうる規則か」**。

| 導出 | 中身 | SQLに寄せる害 |
|---|---|---|
| **最新選択** (max attempt) | ただの「列の最大」。業務規則を含まない汎用の畳み込み | **小**。複製される"規則"は「最大の番号」だけで意味がズレようがない |
| **状態導出** (§3.6) | 3つのイベント表を跨ぐ優先順位つき写像。業務規則そのもの | **大**。「取下＞差戻＞承認済」という業務判断が二箇所に生まれ、変更漏れをコンパイラが検出できない（ドリフト） |

- **複雑だがSQLに置いてよい例**: 申請日時降順＋タイブレークのソート、ページング、全文検索ランキング。複雑でも業務規則ではない。
- **単純だがドメインに置くべき例**: 「消耗品のみは承認免除」（ADR-0004）。実装は boolean 1つでも、業務が決めた規則で将来変わりうる。

### なぜ害になるか：read/write の乖離

「不変条件がインフラに漏れる」の具体的損失は **read/write の乖離**。§3.6 は今、書き込み側（集約 getter）と読み取り側（クエリ）が**同じ1関数**を呼ぶので絶対に食い違えない。SQLに状態導出を複製すると、読み取り側がその関数を共有しなくなり、「集約が思う状態」と「一覧が絞る状態」が静かにズレうる。

害の正体は「複雑だから」でも「導出だから」でもなく、**業務規則の唯一の持ち主が2つに割れ、書き込みと読み取りが矛盾しうるから**。

## 具体化：#571 の各検索条件を層に割り当てる

見積申請一覧（行＝申請または免除を持つバリエーション、状態は最新申請から導出）の検索条件:

| 検索条件 | 対象 | 層 | 理由 |
|---|---|---|---|
| 見積番号（部分一致） | `estimate.estimateNumber`（保存列） | SQL | 事実・attempt不変 |
| 得意先名（部分一致） | `estimate.customer.name`（結合先の列） | SQL | 事実・attempt不変 |
| 納品先名（部分一致） | `estimate.deliveryLocation.name` | SQL | 事実・attempt不変 |
| 有効/無効トグル | `variation.status` | SQL | 事実・attempt不変 |
| 行の包含（申請or免除あり） | 申請行/免除行の存在（EXISTS） | SQL | 事実の照会 |
| 申請状態（5値） | 最新申請の**導出状態**（§3.6） | ドメイン | 業務規則の写像・最新スコープ |
| 申請者名（部分一致） | **最新**申請の申請者名 | ドメイン | 対象が「最新」に依存（※後述の二段構え可） |
| 申請日（期間） | **最新**申請の申請日時 | ドメイン | 同上 |
| 承認待ち役割（roleId） | 最新申請の承認待ちステップの役割 | ドメイン | 業務規則の導出（申請中のみヒット） |

SQLの仕事は「候補バリエーションを不変条件で絞り、各候補の**表示属性**と**イベント行の存在**を最小射影で取る」まで。そこから先（最新申請の選択→状態への畳み込み→導出条件での絞り込み→ソート→limit）はドメイン/サーバのコード。

## 発展

### 最新選択（max attempt）は SQL でも書ける — greatest-N-per-group

「グループごとの最大」は SQL の定番で、少なくとも4通り:

```sql
-- ① 相関サブクエリ
WHERE a.attempt = (SELECT MAX(a2.attempt) FROM estimate_applications a2
                   WHERE a2.variation_id = a.variation_id)

-- ② ウィンドウ関数
ROW_NUMBER() OVER (PARTITION BY variation_id ORDER BY attempt DESC) = 1

-- ③ Postgres の DISTINCT ON
SELECT DISTINCT ON (variation_id) * FROM estimate_applications
ORDER BY variation_id, attempt DESC

-- ④ LATERAL 結合（バリエーションごとに最新1件を横結合）
```

つまり「最新」は状態導出と違いSQLで表現不能ではない。ただし **Prisma の流暢API（`some`/`every`）は greatest-N-per-group を書けず**、やるなら `$queryRaw` に落ちる。

このプロジェクトで最新選択をSQLに寄せない理由:

1. `$queryRaw` に落ちると型安全・mapper・#559 と共有する読み取り経路を捨てる。
2. 最新を切り出しても状態導出（§3.6）は残り、結局ドメイン畳み込みが必要。
3. この畳み込みは「max attempt」より広い。`VariationApplicationState.reduce` は「①免除最優先 → ②最新attemptの状態 → ③未申請」で、**別テーブル（免除）を優先順位つきで跨ぐ**。SQLの最新選択は②の一部しか担えない。

将来、業務量が膨れて申請者/申請日をDB側で厳密に絞らないと遅い、となれば `DISTINCT ON`／ウィンドウでの最新分離は正当な性能レバー（間違いではない）。

### 二段構え：SQLで健全な superset に粗く絞り、ドメインで厳密化

ドメイン側の導出条件でも、**SQLで"健全な上位集合（superset）"に粗く絞ってから**ドメインで厳密化できる。

例: 申請者名の部分一致は最終的には「最新申請の申請者」だけを見たい（ドメイン）が、`applications: { some: { applicant: { name LIKE } } }` で「どれかの attempt に該当者がいる候補」だけSQLで先に絞れば、**取りこぼし無く**（最新が該当なら some も必ず真）候補を減らせる。

**SQL は事実で健全な superset を作り、ドメインが導出値で正確に切る** — これがCQRS読み取りモデルの典型的な形。

## まとめ

覚える一文:

> **SQLに寄せて困るのは "導出だから" でも "複雑だから" でもなく、"それが業務規則で、ドメインが唯一の持ち主だから"。**
> **事実の照会（列比較・範囲・EXISTS）は複雑でもSQL。業務規則の写像・畳み込み・集約の意味はドメイン。汎用機構（最新選択・ソート・ページング）は複雑でも寄せてよい。**

判定手順:
1. その条件の対象は「保存された事実」か「規則を適用して得る導出値」か。
2. 導出値なら、その規則は「汎用機構」か「単一の持ち主を持つ業務規則」か。
3. 業務規則なら、SQLに複製せずドメイン1箇所に置く（read/writeの乖離＝ドリフトを防ぐ）。
4. 性能が要れば、SQLで健全な superset に粗く絞り、ドメインで厳密化する二段構え。
