# 見積単価スナップショットを削除せず維持する判断 — SSoTと導出可能性の議論

作成日: 2026-07-10

## 概要

単価履歴テーブル（共通・得意先別・納品先別、期間行 daterange + 過去不変制約）が整備されたことで、
「見積明細の `unitPrice` スナップショットは SSoT に反する重複であり、履歴から再導出できるので削除できるのでは」
という仮説を検討した。調査の結果、**削除しない**と判断した。

## 詳細

### 削除の前提として成立していた点

- 単価の手入力経路はゼロ（#595 / ADR-0064 で `changeUnitPrice` 系を全撤去、UI は読み取り専用表示のみ）
- 単価マスタの期間行は過去不変（ADR-20260627-86b: 過去開始行の追加不可、現在有効/失効行の編集・削除不可、現在行は適用終了=短縮のみ）
- 価格解決の基準日 `estimateDate` は `Estimate` 集約に永続化済み

→ 理論上 `resolve(商品, 宛先, 見積年月日)` で再導出可能な構造にはなっている。

### それでも削除しない理由（3点）

**1. 再導出の決定性が破れているケースが現存する**

「いつ再導出しても同じ値になる」が成立しない：

- `changeEstimateDate` は価格を再解決しない（#431 未実装）。日付変更後に再導出すると保存時と異なる値になる。宛先変更も同様
- 過去不変制約が守るのは「過去」だけ。**未来日付の見積**が解決した未来の期間行は編集・削除可能で、現在有効行も短縮できる
- #595 以前の手入力時代の見積単価は、マスタ履歴から再現できる保証がない（カラム削除＝不可逆なデータ喪失）
- 複製（`Money.zero()` クリア）・得意先改訂（単価複写）も「基準日での再解決」とは異なる値を持つ

**2. 消してもスナップショットはシステムから消えない**

依存チェーン: `unitPrice → baseAmount/discountedAmount/finalAmount → バリエーション集計5種 → 承認ゴール（税込 finalTotal, ADR-0055）→ deliveryPrice（粗利の真実の源 §8.4）→ 受注（Order は金額を持たず見積参照）`。

- `reconstruct` は保存済み金額を再計算せず信頼する設計（§8.5）。単価だけ導出化すると「単価は導出、金額は保存」の中途半端な二重管理になる
- 金額まで導出化すると、承認済み・受注確定済みの金額が「編集していないのに」動く経路が生まれる（価格ロジック修正、移行 reconstruct、税率変更）。受注がスナップショットを持たないのは見積側の金額凍結が前提（§4.8）
- `RevisedEstimateItemDetail.deliveryPrice` は改訂時点の凍結値で、導出では原理的に代替不可。**SSoT の純度は結局上がらない**

**3. SSoT 論への設計的反論 — 単価マスタと見積単価は「別の問い」に答える**

- マスタ =「日付 X における商品の価格は何か」（ポリシー）
- 見積単価 =「この見積で顧客にいくらと提示したか」（出来事・業務事実。見積書は外部発行文書で監査・契約上の確定値）

両者が通常一致するのは同一性ではなく、再解決契機というプロセスで保たれる一致。
システム設計書 §8.4 も「見積書に印字される確定値のため導出ではなくスナップショットを真実の源とする」と明文化済み。
DDD の語彙では、見積単価はマスタのキャッシュではなく見積集約の属性。

### 一般化できる教訓

- 「履歴テーブルがあれば導出可能」が成立するのは、**導出関数の全入力（基準日・宛先・履歴）が不変なとき**だけ。入力に可変要素が残る限りスナップショットは安全装置として機能する
- イベントソーシング的な「導出できるなら持たない」原則は、導出関数が純粋で入力が不変のときにのみ安全
- マスタと確定値の乖離が課題なら、スナップショット削除ではなく**一致をプロセスで保証する**（#431: 日付・宛先変更/複製/改訂を再解決契機に、#593: 乖離警告）方が既存設計原理（供給元と確定値の分離）と整合する
