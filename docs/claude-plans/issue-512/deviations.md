# Issue #512 実装計画からの逸脱記録

## 逸脱1: delete コマンド分岐のテストをモックリポジトリから実DB結合テストへ変更

### 元の計画内容（Step 3）
- delete コマンドの分岐（空→`repository.delete`、非空→`repository.update`）を、**モックリポジトリ**で
  「`delete`/`update` の呼び分け」を検証するアプリ単体テストで担保する。
- 実装順は Step 3（interface + コマンド分岐）→ Step 4（Prisma delete 実装）。

### 実際の実装内容
- コマンド分岐の検証を、pricing 配下の既存規約どおり**実DB結合テスト**で行った。モック/フェイクは
  一切導入せず、`DeleteXxxPeriodCommand.test.ts` に「最後の1行削除→`findByXxx` が null（空シェルなし）」
  「削除後に同一キーで再登録が version 1 で成功」を追加した。
- これに伴い実装順を **Step 4（Prisma delete）先行 → Step 3（コマンド分岐）** に入れ替えた。コマンドの
  結合テストが実 `repository.delete` を必要とするため。commit は層ごとに分割（Prisma delete → コマンド分岐）。

### 逸脱の理由
- pricing 配下は全コマンド/リポジトリテストが実Prismaの結合テストという強い既存規約で、モックが1つも無い。
  唯一のモックを持ち込むと規約から外れる。
- TDDスキルの `mocking.md` 自身が「Databases — prefer test DB」「メカニズムでなく結果を検証／内部の
  協力者はモックしない」と明記。「`delete` が呼ばれた」を検証するモックは**メカニズム**のテストで
  リファクタに弱い。一方「削除後に `findByXxx` が null（空シェルでなく未設定）」は**観測可能な結果**の
  テストで、#512 の本質（空シェルを残さない・再登録が通る）を直接検証しリファクタに強い。
- 結果として、モックが検証できない「再登録が実際に通る」ところまで踏み込めた。

## 逸脱2: E2E 回帰を新規シナリオでなく既存 Chain A の延長として追加

### 元の計画内容（Step 6）
- 新シナリオ「未設定商品に登録 → 削除 → 未設定表示 → 再登録が成功」を common-selling-prices-crud.e2e.ts に追記。

### 実際の実装内容
- 既存 Chain A（PRD822・register→edit→delete）が UC-5 で「削除→未設定」まで到達済みのため、その直後に
  「#512 回帰: 最終行削除後、詳細に留まったまま再登録できる」を1テスト追加する形にした。新しい商品や
  Chain は起こさず、既存 serial chain の自然な続きとして最小追加した。

### 逸脱の理由
- Chain A が既に「登録→削除→未設定」の状態を作っているため、再登録ステップを継ぎ足すのが最小かつ
  シナリオとして自然。新規 Chain を起こすと seed 商品と重複し E2E が肥大する（ADR-0020 の判断に沿う）。
