# Issue #593 実装の計画からの逸脱記録

計画ファイル: `unit-price-divergence-badge-and-application-warning.md`

全体として計画に忠実に実装した。DTO 名・kind 名・文言など「実装時の裁量」とされた範囲での確定は
逸脱に含めない（各コミットボディに記録済み）。以下は計画の明示的記述と実装が異なった点。

## 1. デデュープの粒度: 全体（提出区分×商品ID）→ バリエーション単位

- **計画**: 解決キーは「提出区分×商品ID」でデデュープ（見積年月日・得意先・納品先はヘッダ不変属性のため
  同一見積内で固定）。文面上は「見積全体で1回」を含意する書き方だった。
- **実装**: 突合ヘルパー `resolveUnitPriceDivergences` を**バリエーション単位**で呼び、その中で商品IDで
  デデュープした。提出区分はバリエーション内で単一なので、1回の呼び出し内では「提出区分×商品ID」キーに
  一致する。ただし異なるバリエーションが同一提出区分・同一商品を持つ場合、バリエーションをまたいだ再解決は
  デデュープされない（例: バリA・バリB がともに得意先宛で商品P を含むと P を2回解決する）。
- **理由**: 突合ヘルパーを Step2（見積詳細・全バリエーション）と Step3（申請preview・単一バリエーション）で
  共有するため、入力単位を「1バリエーションの明細群＋そのバリエーションの提出区分」に統一した。宛先・
  見積年月日はヘッダ不変なので**再解決の結果は必ず同一**（正しさは保たれる）。跨バリエーションの重複解決は
  性能上の軽微な冗長で、見積内のバリエーション数・商品数はいずれも小さいため実害はないと判断した。
  全体デデュープにするとヘルパーが複数バリエーションの提出区分を扱う必要が生じ、Step3 との共有が崩れる。

## 2. `LineDTO.unitPriceDivergence` をオプショナルにした

- **計画**: LineDTO に判別ユニオンを追加。`PrismaEstimateQueryService` は変更しない（事実だけ返す責務を維持）。
- **実装**: フィールドを**オプショナル**（`unitPriceDivergence?`）にした。
- **理由**: 必須にすると LineDTO を組み立てる `PrismaEstimateQueryService.itemToLineDTO` が同フィールドの
  設定を強いられ「変更しない」に反する。オプショナルにすることで query service は事実だけを返し（未設定＝
  合成前）、app 層（`GetEstimateDetailQuery`）が合成時に必ず設定する構成にできた。計画の制約（query service
  非変更・app 層で合成）を満たすための選択で、実質的な設計方針は計画どおり。

## 3. テストビルダー `buildEstimateWithSetGroup` に構成商品の上書きオプションを追加

- **計画**: 明記なし（テスト整備の裁量）。
- **実装**: セット構成明細の乖離を検証するため、`componentProductId` / `componentUnitPrice` オプションを追加した
  （既定は従来どおり `ids.productId`）。共有フィクスチャ商品の販売単価を書き換えると並列実行で衝突するため、
  乖離テストは専用商品を構成明細に差し込む必要があった。
