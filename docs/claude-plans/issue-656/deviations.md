# Issue #656 実装計画からの逸脱

## 1. 検証 A で落ちたのは `static` ではなく `test` だった（計画が置いた前提の誤り）

- **元の計画**: Step 4 の確認項目に「`static` ジョブで落ちる（＝ `next build` が `*.test.ts` も型検査しているという `ci.yml` の前提の実地確認）」を置いた。
- **実際の結果**: `f500a1a2` の push run は `static: success` / `test: failure` だった。**`static` は素通りした。**
- **Step 4 の主目的は達成している。** 「stale base の緑でマージできる → develop が壊れる → 検知される → 犯人が一意に特定できる」という因果の連鎖は想定どおり全て成立した（下表）。逸脱したのは「どのジョブが検知するか」の予測のみである。

  | 確認項目 | 結果 |
  |---|---|
  | #675 マージ後も #676 の checks が再実行されない | ✅ `static` / `test` とも 01:05 完了のまま |
  | 古い base に対する緑でマージが許可される | ✅ `MERGEABLE` / `CLEAN`（PR の base は `297617fa`、develop は `4c7a9d16`） |
  | develop の push run が赤くなる | ✅ `f500a1a2` = `failure` |
  | 緑 → 赤の境界が現れ犯人が一意に読める | ✅ `297617fa` 緑 → `4c7a9d16` 緑 → `f500a1a2` 赤 |
  | 3 コミットすべてに verdict が残る | ✅ SHA 単位 concurrency が効いている |

- **原因**: `ci.yml`（および #643 の `deviations.md` 逸脱 3）が書いている「`next build` は tsconfig の `include`（`**/*.ts`）で定義されたプログラム全体を検査し、`scripts/` や `*.test.ts` も対象に含む」のうち、**`*.test.ts` の部分が成り立っていない**。

  ローカルで境界を特定した（Next.js 16.0.7、いずれも「誰も import しないファイルに型エラーを 1 つ仕込む」プローブ）。

  | プローブ | `tsc --noEmit` | `next build` |
  |---|---|---|
  | `scripts/__typecheck-probe.ts` | ❌ TS2322 | ❌ Failed to compile |
  | `scripts/__probe.test.ts` | ❌ TS2322 | ✅ exit 0 |
  | `src/server/__tests__/helpers/__probe.ts` | ❌ TS2322 | ✅ exit 0 |
  | 検証 A の実物（`__tests__/**/*.test.ts`） | ❌ TS2724 | ✅ exit 0 |

  除外の基準はモジュールグラフ上の到達可能性ではなく、**ファイル名とディレクトリ名**である。Next は型検査プログラム自体には全ファイルを含めたうえで、診断を出力する直前にパスで捨てている（`next/dist/lib/typescript/runTypeCheck.js` の `/[\\/]__(?:tests|mocks)__[\\/]/` と `/(?<=[\\/.])(?:spec|test)\.[^\\/]+$/`）。「検査していない」のではなく「検査結果を黙って捨てている」。

  #643 が `scripts/` で行った実測自体は正しく、そこから `*.test.ts` へ一般化した推論だけが誤っていた。プローブの置き場所がたまたま捨てられない側だったため差が出なかった。

- **本 issue では直さない。** `ci.yml` のコメント訂正と独立した型検査ステップの復活は **#678** として起票した。理由は 2 つ。
  1. 本 issue のスコープ（マージ後の検査 run の不在）と別の関心事であり、#643 の判断（`tsc --noEmit` ステップの削除）の再評価という独立した設計判断を含む。
  2. 復活のさせ方（ステップか独立ジョブか）は required status checks の照合キーに影響し、ruleset の更新とセットになる。本 issue が触っている ruleset 設定と同じ PR で動かすと、strict 化の検証結果が読めなくなる。

- **Step 8（検証 B）の題材は変更不要。** 検証 B が確かめるのは「base が古い PR のマージが止まること」と「Update branch 後に PR 段階で赤くなること」であり、どのジョブが赤くなるかには依存しない。ただし**確認項目から `static` の記述を落とす**こと（同じ題材では `test` が赤くなる）。

## 2. 使い捨て PR に E2E も走った（想定していなかったコスト）

- **元の計画**: 検証用 PR のコストを `ci` の 2 ジョブとして見積もっていた。
- **実際**: 題材が `src/` 配下のため `playwright.yml` の `paths` に合致し、PR X / Y / revert のそれぞれで E2E 7 ジョブが起動した（計 27 ジョブ）。
- **影響なし**: public リポジトリのため課金は無く、同時実行枠（20）にも当たらなかった。すべて緑。記録のみ。
