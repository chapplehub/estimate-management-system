## 背景

E2E の shard 分割（#645 / ADR-20260727-55f）で CI は 9 分 33 秒 → 4 分 41 秒まで短縮された。
ADR は shard 数を**可変パラメータ**と位置づけ、初期値 4 を選んだ理由を「準備一式の重複により
短縮率が逓減し、4 → 6 の追加短縮は約 41 秒にとどまるため」と記録している（ADR L101）。

Issue #660 はこの 41 秒を取りに行く判断である。したがって本 Issue は
**ADR が明示的に見送った選択を、実測を根拠に採る**ものであり、値の変更だけでなく
ADR 側の記述更新を伴う。

### 直近実測（run 30328193465 / 2026-07-28）

| 項目 | 実測 |
|---|---|
| 準備一式（Set up job 〜 Playwright install） | 69〜76 秒 |
| `Run Playwright tests` | 141 / 143 / 152 / 166 秒（合計 602 秒） |
| 最重 shard ジョブ全体 | 236 秒（shard 4） |
| run 全体（merge 27〜31 秒 含む） | 281 秒 = 4 分 41 秒 |
| 偏り | 1.18 倍（166 / 141） |

### 6 分割の予測

#645 の計画（`shard-e2e-workflow-with-report-merge.md:155-163`）が導いた
「shard 内固定費 F（dev server 起動 + JIT コンパイル）＋ 可変部 V」のモデルを、
上の実測で再校正する。平均テスト時間 150.5 秒 = F + V/4、F ≈ 19 秒 より **V ≈ 526 秒**。

- N=6 のテスト時間 = 19 + 526/6 ≈ **107 秒**（偏り 1.1 倍込みの最重 shard で約 117 秒）
- shard ジョブ = 準備 70 秒 + 117 秒 + upload/post 約 8 秒 ≈ **195 秒（3 分 15 秒）**
- run 全体 ≈ 195 + merge 31 秒 + ディスパッチ約 10 秒 ≈ **236 秒（3 分 56 秒）**
- **短縮見込み 約 45 秒**。ADR の予測 41 秒とほぼ一致する

件数分布は `playwright test --list --shard=i/6` で実測済み: **65 / 63 / 63 / 63 / 66 / 60**（均等）。

ランナー時間は 4 × 236 秒 = 944 秒 → 6 × 195 秒 = 1170 秒で **約 1.24 倍**。
リポジトリは PUBLIC のため GitHub-hosted runner は無料であり、コスト面の不利はない。
同時実行ジョブ数は playwright 6 + ci.yml 2 = 8 で、標準 runner の上限 20 に余裕がある。

## 設計判断

### shard 数を 4 → 6 に上げるか

- A. 据え置く（ADR の初期判断を維持）
- B. 6 に上げる
- **採用: B**（Issue #660 の指示）。短縮幅 約 45 秒に対しランナー時間 1.24 倍。
  PUBLIC リポジトリで Actions 分が無料であるため、トレードオフの片側にコストが立たない。
  ADR が「実測を見て見直す」と明記した通りの運用にあたる。

### ADR-20260727-55f の扱い

- A. 既存 ADR の「影響」を更新する
- B. 新規 ADR を起票する
- C. 触らない
- **採用: A**（ユーザー判断で確定）。本 Issue は ADR の**決定**（shard 分割方式・`workers: 1` 据え置き）
  を変えていない。変わるのは決定の下にある可変パラメータの値なので、新規 ADR は立てず、
  L101 の「初期値は 4」を実測ベースの経緯に書き換えて最終更新日を更新する。
  触らない選択は、ADR に「初期値は 4」と書かれたまま実態が 6 になり、
  次に読む人が矛盾に突き当たるため採らない。

### `timeout-minutes: 20` の扱い

- A. 20 分据え置き
- B. 15 分に下げる
- C. 10 分に下げる
- **採用: A**（ユーザー判断で確定）。安全網の性質上、緩すぎて困ることは少ない。
  ただし L41-42 のコメントは 4 分割前提の数値（最悪ケース 約 7 分 20 秒）なので、
  6 分割ベース（約 6 分 30 秒）に更新する。**値ではなく根拠が陳腐化する**のを防ぐため。
- `merge-reports` の `timeout-minutes: 10` は shard 数に依存しないため変更しない。

### スコープ外とした判断

- **準備一式（約 70 秒/shard）の短縮**: 別 Issue に切る（ユーザー判断で確定）。
  Playwright ブラウザのキャッシュ化などで 20〜25 秒相当の余地があるが、
  shard 数の効果測定と混ざると評価が濁る。本 Issue 完了後に起票する。
- **`workers` の引き上げ**: ADR の決定事項として不採用のまま。`toHaveCount` 100 箇所の
  前提監査を伴うため、shard 数の調整とは別スコープ。
- **shard への手動振り分け**: 不要。6 分割の件数分布 65/63/63/63/66/60 は均等で、
  ADR-20260727-55f 選択肢 D の「最後の手段」に踏み込む状況にない。
- **`merge-reports` ジョブ・`concurrency`・`paths` フィルタ**: 変更不要。
  ジョブ名は `${{ matrix.shardTotal }}` を参照し、blob の download pattern は
  `blob-report-*-${{ github.run_attempt }}` とワイルドカードのため shard 数に依存しない。

全 6 shard + `e2e report` が **success**。

- **モデルの妥当性が実証された**: テスト時間の平均 106.5 秒に対し予測は 107 秒（`F + V/6 = 19 + 526/6`）。
  `F + V/N` 分解は shard 数を変えても予測力を持つ。
- **統合レポート 380 件** ＝ 実テスト 368 + `setup` 2 × 6 shard。期待値どおり。
  件数分布 65/63/63/63/66/60 はローカルの `--list` 実測と完全一致した。

  **4 分 02 秒**（最重 shard 195 秒 + merge 34 秒 + ディスパッチ）で、想定 3 分 56 秒とほぼ一致。

#### 偏り 1.82 倍の評価（判定閾値 1.5 を超過 → shard 数は 6 で据え置き）

テスト時間の偏りは 140 / 77 = **1.82 倍**で、#645 で採用した閾値 1.5 倍を超えた（4 分割時は 1.18 倍）。
それでも shard 数を動かさない判断としたのは次の理由による。

- shard 5 の 140 秒は、`install` が 20 倍遅かったのと**同一ランナー上**での測定であり、
  テストだけが正常速度だったとは考えにくい。**shard 5 を除くと 77〜112 秒で 1.45 倍**と閾値内に収まる。
- skew を押し上げているのは「shard 5 が重い」よりも「shard 2 が 77 秒と際立って軽い」ほう。
  律速するのは最重 shard であり、その 195 秒は想定どおりで短縮目標も達成している。
- 1 run 分のデータで可変パラメータを動かすと、次の run で揺り戻す。数 run 観測してから判断する。

なお **手動振り分けは検討していない**（ADR-20260727-55f 選択肢 D は最後の手段という位置づけ）。

  **この失敗モードの経路そのものを消す（＝ 安定性）**という価値を持つ。

## 検証

CI 設定の変更のためローカルでの完全な再現はできない。次の順で確認する。

1. **ローカル（プッシュ前）**: `pnpm exec playwright test --list --shard=i/6` を i=1..6 で流し、
   合計が全テスト件数と一致し、各 shard が空でないことを確認する（測定済み: 65/63/63/63/66/60）
2. **YAML 構文**: `.github/workflows/playwright.yml` を `gh workflow view` もしくは
   `actionlint` があれば流す。無い場合は PR 作成時に GitHub 側が構文エラーを出すため、
   run がディスパッチされること自体を確認とする
3. **実 run（Step 3）**: PR を作成し、6 shard + `e2e report` が緑で完走することと、
   統合レポートの件数・所要時間を上表の想定と突き合わせる

E2E をローカルで全体実行することはしない（変更に関係するスペックのみ、全体は CI に任せる方針）。
