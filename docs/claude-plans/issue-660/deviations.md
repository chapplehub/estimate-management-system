# Issue #660: 実装計画からの逸脱

## 1. ADR の「4 shard 中 1 つが赤なのに」という例示を shard 数非依存の表現に変えた

- **計画**: Step 1 の対象は ADR「影響」L101 の shard 数の記述と最終更新日のみ。
  「L102 は変更しない」「決定・根拠セクションは変更しない」とだけ書いており、
  他の行への言及はなかった。
- **実際**: 上記に加え、L107 の「持たせないと『**4 shard 中 1 つ**が赤なのに統合ジョブは緑』が
  常態化する」を「**一部の shard** が赤なのに〜」に変更した。
- **理由**: 計画立案時の grep が「4 分割前提の記述」を L84（選択肢 D の件数分布）だけと見て
  取りこぼしていた。実装時に再検索して発見した。この行は統合ジョブの責務を説明する例示で、
  shard 数を具体値で書く必要がない。数値を持たない表現にすれば以後の shard 数変更で
  この行を触らずに済むため、値を 6 に書き換えるのではなく shard 数非依存にした。
  なお L84 の件数分布 96 / 92 / 94 / 94 は「（4 分割）」と明記された**当時の実測記録**なので、
  現在値に合わせず原文のまま残している。

## 2. `timeout-minutes` の根拠コメントの基準を「ジョブ全体」に明示した

- **計画**: Step 2 で「実測を『2〜3 分』→『2 分前後』に改める」。
- **実際**: 「6 分割後の**ジョブ実測** 3 分前後」と書いた。
- **理由**: 元の「実測 2〜3 分」がテスト実行部分を指すのかジョブ全体を指すのかが曖昧で、
  そのまま数値だけ差し替えると曖昧さを引き継いでしまう。安全網の妥当性を判断するには
  ジョブ全体との比較が必要なため、基準を明示した上でその値（実測 148〜195 秒）を採った。
  計画が想定した「2 分前後」はテスト実行部分（実測平均 106.5 秒）に相当する。

## 3. ADR 選択肢 D の「shard 数の引き上げの方が優れている」に反証の注記を追加した

- **計画**: Step 1 で「ADR の**決定・根拠セクションは変更しない**（方式選択は変わっていないため）」。
  「検討した選択肢」セクションへの言及もなかった。
- **実際**: 選択肢 D（L86）の「偏りへの対処としては**手動振り分けより shard 数の引き上げの方が
  優れている** —— 最重 shard の中身自体が減るため、保守コストゼロで同じ効果が得られる」に、
  #660 の実測で反証された旨の注記を追加した。原文は削除せず残している。
- **理由**: 計画立案時は「shard 数を上げれば偏りは改善する」という ADR の前提を疑っていなかったため、
  この記述が検証対象になるとは想定していなかった。Step 3 の実測で N=4 → 6 により偏りが
  1.18 倍 → 1.52 倍に**悪化**し、この主張が誤りだと判明した。実測で否定された主張を注記なしに
  残すと、次に shard 数を触る人が誤った前提から出発する。当時の判断記録としての価値は
  あるため原文は残し、反証を注記する形にした。

## 4. Step 3 の 1 回目の実測評価が誤っており、2 回目の実測で訂正した

- **計画**: Step 3 は 1 回の run で実測を確認する想定。
- **実際**: 1 回目（run 30337033582）で「shard 5 の 140 秒は install が 415 秒かかったのと
  同一ランナー上の測定だからランナー不調の疑い」「shard 5 を除けば 1.45 倍で閾値内」
  「正常時推定 4 分 02 秒・約 39 秒短縮」と評価したが、**いずれも誤りだった**。
  2 回目（run 30338166399、install 22 秒と正常）でも shard 5 は 137 秒で最重となり、
  run 全体は 270 秒。実効短縮は約 11 秒（想定 45 秒）と判明した。
- **理由**: 外れ値を引いた run 1 本で「外れ値を除けばこうなるはず」と補正推定したのが誤り。
  補正は最重 shard がどれかという前提に依存するのに、その前提自体が外れ値に汚染されていた。
  2 回目のデータは、docs のみの追加 push で run が再実行された（`pull_request` の `paths`
  フィルタは PR 全体の変更ファイルで評価されるため）ことで偶然得られたものであり、
  意図して 2 run 観測したわけではない。

## 逸脱ではないが記録しておく判断

### 偏りが閾値を超えたが shard 数を 6 で確定した

計画の Step 3 は「最重 shard が最軽 shard の 1.5 倍を超えていないか確認する。超えていた場合も
**手動振り分けは行わない**。6 のまま据え置くか更に引き上げるかを実測値とともにユーザーへ提示する」
としており、閾値超過はこの分岐の想定内。実測（1 回目 1.82 倍 / 2 回目 1.52 倍）と
実効短縮が約 11 秒にとどまることを提示し、**6 で確定**の判断を得た。
根拠は計画ファイル本体の Step 3 実測結果に記載。
