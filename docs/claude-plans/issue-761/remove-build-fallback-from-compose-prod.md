# Issue #761: 本番デプロイで pull 失敗時に EC2 上ビルドへ暗黙フォールバックする経路を塞ぐ — 実装計画

> **実行規約**: 各 step 完了時にこのファイルの該当チェックボックス（`- [ ]`）を
> `- [x]` に更新し、その更新を step のコミットに含めること。

## 概要

`compose.prod.yaml` の `app` / `migrate` は `image:` と `build:` を併記している。この形では pull に
失敗したときに compose がエラー終了せず、**EC2 上のチェックアウトからのローカルビルドへ暗黙に
フォールバック**する。`build:` セクションを削除してこの経路を構造的に断つ。

あわせて、`build:` の存在を前提にした記述が嘘になる 2 箇所（`release-image.yml` のコメント、
learning ノート）を実態に合わせる。

方式そのもの（`build:` 削除 / `pull_policy: always` 不採用）は #763 の設計セッション（2026-08-18）で
合意済み。本計画では /grill-with-docs セッション（2026-08-29）で詰めた残りの論点と、その場で取った
実測結果を記録する。

### compose の実挙動（Docker Engine 28.3.3 / Compose v5.4.0 / Storage Driver overlay2 で実測）

| プローブ | 条件 | 結果 |
| --- | --- | --- |
| A | 既定（`pull_policy: missing`）／ローカルに同名イメージあり | `Pulling` 行が**一切出ず**起動。EXIT=0 |
| B | `pull_policy: always` ＋ `build:` 併記／ローカルにもレジストリにもイメージ無し | **起動する**（＝ビルドされた）。EXIT=0 |
| C | `pull_policy: always`／`build:` 無し・**ローカルに同名イメージあり**・レジストリで pull 失敗 | `Error ... denied` で起動せず。EXIT=1 |

- A は「`up -d` 単体では新しい `latest` を取り込まない」（stale latest 問題）の直接的な裏付け
- B は「`pull_policy: always` はフォールバック経路を塞がない」ことの裏付け
- C は「`build:` 削除後に `always` を足すと、ローカルにイメージがあってもレジストリ到達不能時に
  起動できなくなる」ことの裏付け
- **イシュー本文の補足「`pull_policy: always` はローカルタグに対して pull 失敗の警告を出すが、
  ローカルイメージがあれば起動自体は成功する」は再現しなかった**（C で EXIT=1）。B と突き合わせると、
  judge は `build:` 併記のまま測って「起動成功」を観測した可能性が高く、成功していたのは
  pull フォールバックではなく**ビルド**だと考えられる。この訂正は PR 本文に残す

### ローカル検証への影響

- `docs/ops/prod-docker-local.md` の Step 2 は既に `docker build --target runner -t ems-app:local .` の
  明示ビルドで、`build:` セクションに依存していない
- `seed` サービスは現状でも `build:` を持たず `MIGRATE_IMAGE` 参照のみで機能している
  ＝ `build:` なしでローカル検証が回ることは実証済み
- GHCR のイメージは arm64 単一アーキ（ADR-20260818-7pn）。x86_64 の開発機では `APP_IMAGE` /
  `MIGRATE_IMAGE` の上書きは作法ではなく**必然**であり、`build:` 削除のローカル影響はゼロ

## 設計判断

### 1. 塞ぎ方の方式

- A. `pull_policy: always` を入れる / B. `build:` セクションを削除する / C. デプロイスクリプトで
  `docker compose pull` を必須手順にする
- **決定: B**（#763 セッションで合意、本セッションで実測により補強）
- 理由: A は 2 つの意味で不適格。(1) `build:` を残したままでは経路を塞げない（プローブ B）。
  (2) `build:` を消した上で足すと、ローカルに正しいイメージがあってもレジストリ到達不能なだけで
  起動できなくなる（プローブ C）。GHCR 障害中や EC2 のネットワーク不調時に「今動いているものと
  同じイメージでコンテナを作り直す」ができなくなる。`always` が買える唯一のもの（stale latest の
  解消）は C の明示的な `docker compose pull` が同等以上に提供する（`pull` は取りに行くことだけが
  仕事なのでフォールバック先を持たず、失敗すれば素直に非ゼロで止まる）
- **「取りに行く」と「起動する」を別コマンドに分けておけば、前者が失敗しても後者の能力は残る。
  `always` はこれを 1 つに癒着させる設定である**——これが不採用の本質

### 2. ローカル検証と本番でファイルを分けるか

- A. 本番ファイルから `build:` を落とし、ローカル検証用 overlay を別ファイルに置く / B. 分けない
- **決定: B（分けない）**。`compose.prod.yaml` 一枚 ＋ `APP_IMAGE` / `MIGRATE_IMAGE` の値だけで
  切り替える
- 理由: (1) `compose.prod.yaml:3-4` が「dev 用とは独立したファイル（overlay にしない。継承関係は
  事故のもと）」と既に反対の立場を明文化している。(2) overlay は `build:` を別ファイルへ移すだけで
  経路を消していない（`-f` を 2 つ渡せば復活する）。買いたいのは経路の**構造的な不在**であって
  移設ではない。(3) ローカル側に需要が無い（前提の裏取り参照）

### 3. stale latest（`up -d` が既存ローカルタグを再 pull しない）の扱い

- `build:` 削除は「無言のビルド」を消すが、「EC2 に残った古い `latest` で無言に起動する」経路は
  残る（プローブ A）。これを塞ぐのは #784 が定義する明示的な `docker compose pull`
- **決定: 本イシューでは compose のコメントに「事実」だけを 1 行残し、手順は書かない**。
  「`pull` を必須とする」は #784 が `docs/ops/deploy.md` で定義する規範であり、compose 側に書くと
  二重管理になる。一方 compose の挙動そのものはこのファイルの読者が知るべき事実

### 4. ADR を起票するか

- **決定: 起票しない**
- 理由: スキルの 3 基準のうち「覆すコストが高い」を満たさない（`build:` を戻すのは 3 行の追記）。
  加えてこの決定の寿命は短い可能性がある——#784 が `deploy.sh` で `pull` を必須にした時点で
  「イメージ供給の担保はデプロイ手順側にある」という上位構造が確立し、`pull_policy` を巡る議論
  そのものが成立しなくなる
- 代わりに手当てすべきは**却下案の再提案リスク**（`pull_policy: always` は直感的に正しく見えるため
  再提案されやすい）。これは compose のコメント 2 行で足り、読まれる場所にも置ける
- `CONTEXT.md` は見積業務の用語集であり、インフラの語彙は載せない方針のため更新対象なし

### 5. EC2 実機への反映

- **決定: 本イシューでは EC2 に触らない**。#784 のデプロイ手順整備時に `git pull` 経由で届くのに任せる
- 理由: (1) EC2 が追うのは `main`（#784 の決定。`latest` = main の写像という不変条件と整合する唯一の
  選択）なので、develop へのマージ時点では**そもそも EC2 に届く筋合いがない**。(2) #784 は
  「EC2 上でファイルを直接編集しない」「`git pull --ff-only` が drift の検出器を兼ねる」を規範化する
  方針で、その手順の確立前に個別に触ると防ごうとしている状態を自分で作る。(3) 空白期間のリスクが
  小さい（暗黙ビルドが起きるのは誰かが手で `up -d` を叩き、かつ pull に失敗したときだけで、
  その運用自体がまだ定義されていない）

## 検証

削除前（Step 2）／削除後（Step 4）で同一の 3 ケースを実行し、結果を PR 本文に記録する。
nginx を含む全体起動はローカルでは証明書が無くて成立しないため（`docs/ops/prod-docker-local.md`
の注意点）、`--no-deps` で単一サービスに絞る。

| # | 条件 | 期待（削除前） | 期待（削除後） |
| --- | --- | --- | --- |
| 1 | 存在しない SHA タグ（`APP_IMAGE=ghcr.io/.../app:sha-deadbee`） | `Building` へフォールバックして起動 | 解決失敗で**非ゼロ終了** |
| 2 | ローカルタグ（`APP_IMAGE=ems-app:local`） | 起動する | 起動する（回帰なし） |
| 3 | `APP_IMAGE` 未設定（既定の GHCR `latest`） | pull 失敗 → ローカルビルドで起動してしまう | pull は警告付きで成功し、コンテナ起動時に `exec format error` で非ゼロ終了 |

ケース 3 を含める理由は、これが**将来の開発者が最初に踏むケース**だから。従来は変数の設定を
忘れてもローカルビルドで動いてしまい事故に気づけなかったが、削除後は必ず止まる。ただし出るのは
arm64 とも `APP_IMAGE` とも書かれていないエラーなので、文言を確認した上でコメント追記の要否を
判断する。

プローブ A / B / C（`pull_policy` の挙動）の結果と、それに基づくイシュー本文の訂正も PR 本文に含める。
