# Issue #549: test: 納品先別販売単価 保守画面のE2Eテスト — 実装計画

## Context

親 #544 の分割のうち **E2E** 担当（得意先別 #509 の納品先版）。管理画面（#547/#555）と一覧画面（#548）が
揃ったため、横断的にE2Eを整備する。調査の結果、以下が判明した:

- **一覧画面E2E** (`delivery-location-selling-prices-list.e2e.ts`) と **`seedDeliveryLocationSellingPrices`**
  （D902×PRD870-875）は #548 で既に着地済み。ただし一覧の「管理画面への遷移」テストは #547 未着地当時の
  暫定で **href 検証のみ**（実クリックせず）。
- **管理画面本体**（`[deliveryLocationCd]/[productCd]/`）は #555 で実装済み（PeriodForm / ReviseForm=改訂
  ウィザード / PriceTimeline / PeriodDeleteConfirm）。
- **未着手**は管理画面（**CRUD**・**詳細/タイムライン**）のE2Eと、そのための**可変フィクスチャ**。

納品先別だけの固有機能は詳細タイムラインの **3段フォールバック（納品先別→得意先別→共通）3レーン構成**
（共通は1レーン・得意先別は2レーン＝納品先別が1段深い）。これが issue の「共通/得意先別単価への
フォールバック表示」の検証対象。

**テンプレートは得意先別 #509（PR #541・rebase で develop に取込済み）が最良の先行事例**
（`customer-selling-prices-crud.e2e.ts` / `-detail.e2e.ts`）。納品先軸・フォールバックタイムライン・
「上書きなし＝正常状態」文言まで同型で、差分はタイムラインの**3レーン化**（得意先別が主レーンと共通の間に
1段挟まる）と宛先キーが `(deliveryLocationCd, productCd)` になる点のみ。

**隔離原則（#509 の C904 パターン踏襲）**: 変更系は商品コードではなく**スコープ軸（納品先）で隔離**する。
一覧ビューが納品先スコープのため、CRUD 用に**専用納品先 D904**（既存 C903 配下）を新設し、読取系 D902 帯は
一切変更しない。Playwright は `workers: 1`（並列なし）＋ファイル名順 crud→detail→list のため、変更系の
途中状態が読取系へ漏れる経路は原理的に無い。

**副作用調査済み（破壊的変更ゼロ・全て新規追加）**:
- PRD876-879: 全リポジトリ未使用（空き）。
- 新規納品先 D904（C903配下・東京・"CRUD納品先"命名・有効）: `delivery-locations-list` の件数断定は全て
  他納品先スコープ（"山田"/"D003"/"山田製作所"/"大阪"）、状態フィルタは意図的に件数非結合のため無影響。
- C903 への得意先別単価追加: C903 は他テスト非参照。得意先一覧の件数断定は他得意先スコープ。
- 商品 PRD876-879 追加: `products-list`/見積系に総数結合の断定なし（#541 が PRD866-869 追加済み・同型前例が緑）。

## 設計判断

### E2Eファイル構成 → crud + detail の2ファイル追加（確定）
- 得意先別 #509 に倣い `-crud.e2e.ts` / `-detail.e2e.ts` を新規追加。既存 list e2e は残し、暫定だった遷移テストのみ
  実クリックへ格上げ。3ファイル体制（crud/detail/list）で得意先別・共通と揃える。

### 3段フォールバックタイムラインの検証 → 専用フィクスチャで3レーン全埋め（確定）
- 詳細リッチ母体 **PRD876** に **納品先別(D904)+得意先別(C903)+共通** の3層を持たせ、主レーン
  （`price-timeline-bar`）＋得意先別レーン＋共通レーン（`price-timeline-secondary-bar`）がすべて帯付きで
  描画されることを検証。得意先別 #509 の2レーン検証（`secondary-bar` count=1）を3レーンへ拡張したもの。

### 非管理者（一般ユーザー）権限検証 → 含める（確定）
- 得意先別 #509 に倣い crud e2e に storageState 切替の一般ユーザーセクションを設け、閲覧可・ミューテーションUI
  （操作列ヘッダ／新規追加・編集・適用終了・削除ボタン）が一切描画されないことを検証。

### 変更系の隔離単位 → 専用納品先 D904 を新設（#509 の C904 パターン踏襲・推奨）
- 変更系は商品ではなく納品先で隔離（一覧が納品先スコープのため）。既存 C903 配下に CRUD 専用納品先 D904 を
  追加し、読取系 D902 帯は不変に保つ。D904 は「東京・"CRUD納品先"命名・有効」とし一覧検索の件数断定に触れない。

### フィクスチャ配置 → `seedDeliveryLocationSellingPrices` を拡張（推奨）
- 得意先別（単一 `seedCustomerSellingPrices` が一覧+CRUD帯を兼務）に倣い、既存 `seedDeliveryLocationSellingPrices`
  に保守帯（D904×PRD876-879）を追記（新関数を割らない）。得意先別フォールバック層の投入用に
  `insertCustomerPeriod` ヘルパーと C903×PRD876 の `customerSellingPrice` 集約作成を同関数内へ追加。

### PRD876 の二役共用 → 詳細（バッジ/操作出し分け/3レーンタイムライン）＋ CRUD重複拒否母体で共用（推奨）
- 得意先別の PRD866（詳細E2E＋crud重複拒否母体・DB不変）踏襲。納品先別3期間（失効/現在有効/将来）が両用途を満たす。
- 無効商品/無効納品先の詳細表示は既存の読取専用フィクスチャ（PRD875=無効商品 / D903=無効納品先）を再利用し追加投入しない。

## 検証（Verification）

- **seed 健全性**: `pnpm e2e:seed` が D904 と PRD876-879、および PRD876 の3層フィクスチャ（納品先別3期間＋
  得意先別1＋共通1）をエラーなく投入すること（EXCLUDE制約＝適用期間重複不可を半開区間の隣接で満たす）。
- **E2E**: 対象3スペックが全パス。特に検証すべき観点:
  - detail: 3レーンタイムラインで得意先別・共通レーン双方に帯が出る（フォールバック全埋め）。
  - crud: 改訂ウィザードで旧行終了＋新行連続追加（重複エラー不発）、空状態の納品先別固有メッセージ、
    一般ユーザーのミューテーションUI完全非表示。
  - list: 実クリックで管理画面へ着地。
- 実行方式・使用データ・命名は ADR-0012 / 0017（ヘッダ名ベースのセル特定）/ 0020（serial分割・today相対seed）に準拠。
  テスト内で Prisma クライアントを直接使わない。
