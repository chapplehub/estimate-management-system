# Issue #602: 実装計画からの逸脱

計画: `carry-set-groups-on-duplicate-and-revise.md`

## 1. Step 4 の回帰テストを「改訂パス」で書いた

- **元の計画**: 既存見積（セット群なし）に、セット群付きの**新バリエーションを追加**して `update` するケースを追加し、群衛星＋交差表が新規 INSERT されること・既存群が `deleteMany(notIn)` に巻き込まれないことを検証する。
- **実際の実装**: セット群付き（納品先宛）の見積を insert したうえで **`reviseForCustomer` して `update`** するケースにした（`update: 改訂で生まれたセット群が既存見積に新規 INSERT され、改訂元の群も残る（#602）`）。
- **逸脱の理由**: 計画が守ろうとした永続化上の関心は「既存見積に対して群衛星＋交差表が新規 INSERT される（＝insert 経路ではなく update の差分 upsert 経路を通る）」ことだった。改訂パスはこの関心をそのまま通過したうえで、**改訂元の群が `deleteMany(notIn)` に巻き込まれない**ことも同時に固定できる（計画では別々に検証するつもりだった 2 点が 1 本に収まる）。加えて #602 が実際に壊れていた経路そのものなので、回帰ガードとしての意味が強い。

## 2. テストビルダーに `submissionType` オプションを追加した

- **元の計画**: Step 4 の対象ファイルは `PrismaEstimateRepository.test.ts` のみ。
- **実際の実装**: `estimateAggregateBuilder.ts` の `buildEstimateWithSetGroup` に `submissionType` オプションを追加した。
- **逸脱の理由**: 上記 1 の変更に伴い、改訂元にできる**納品先宛**のセット群付き見積が必要になったため（既存のビルダーは提出区分が得意先宛に固定されていた）。既定値は従来どおり `SubmissionType.CUSTOMER` で、既存テストの挙動は変えていない。

## 3. 複製に単価解決欠落の異常系テストを 1 本追加した

- **元の計画**: Step 3 のテスト観点は「Step 2 と対称（`deliveryPrice` を除く）／単価マップのキーが `提出区分:商品ID` である点」。
- **実際の実装**: 上記に加えて「構成明細の単価が複製元の提出区分で解決されていないと `BusinessRuleViolationError`」を追加した。
- **逸脱の理由**: 「キーが `提出区分:商品ID` である」ことを正常系だけで示すと、キー体系が壊れても偶然通りうる。構成明細の商品を欠いたマップで拒否されることを示して初めて、構成明細が通常明細と**同じキー体系**で解決されていることが固定される。
