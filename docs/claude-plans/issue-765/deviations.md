# Issue #765 実装計画からの逸脱記録

計画: `reuse-dev-seed-for-public-demo-bootstrap.md`

## 1. migrate ステージに `tsconfig.json` も COPY した

- **元の計画**: Step 2 で `prisma/` と `src/` を丸ごと COPY する（設計判断 #9）
- **実際の実装**: `prisma/` `src/` に加えて `tsconfig.json` も COPY した
- **理由**: `prisma/seed-dev-data/*.ts` が `@server/*` / `@subdomains/*` のパスエイリアスで
  ドメイン層を参照しており、tsx はその解決に `tsconfig.json` の `paths` を読む。計画時点では
  seed 本体（`seed-dev.ts`）の相対 import しか把握しておらず、この依存を見落としていた。
  設計判断 #9 が警告していた「実行時にしか壊れない漏れ」そのものであり、方針の変更ではなく
  同じ方針の適用漏れの修正にあたる

## 2. seed の env 判定を `??` ではなく `||` にした

- **元の計画**: Step 1 で `DEFAULT_PASSWORD` を `process.env.SEED_DEFAULT_PASSWORD ?? "pass123!"` にする
- **実際の実装**: `||` で判定する（Step 3 のコミットで変更）
- **理由**: `.env.production` に `SEED_DEFAULT_PASSWORD=`（空値）と書かれた場合、compose は
  それを「設定済みの空文字」として渡す。`??` は空文字を設定済みと見なすため、空パスワードで
  アカウントが作られてしまう。`||` なら空値も未設定として扱える。
  併せて compose 側の `environment` をリスト形式の値なし記法（`- SEED_TOTAL_EMPLOYEES`）に
  した。マップ形式 `KEY: ${VAR}` は未設定時に空文字を渡してしまうため

## 3. `SEED_TOTAL_EMPLOYEES` に下限ガードを追加した

- **元の計画**: Step 1 は「値の外出し」のみ。バリデーションは計画に無い
- **実際の実装**: `TOTAL_EMPLOYEES < FIXED_ACCOUNT_COUNT`（= 26）で例外を投げるガードを
  モジュール評価時に追加した
- **理由**: Step 5 の検証で `SEED_TOTAL_EMPLOYEES=20` を試したところ `seedDevEstimates` が
  前提マスタ不足で失敗した。連番の割当が `[1..23]` 役割持ち → `[24..26]` 固定課員 →
  残りランダム という構造で、見積 seed は 24 番目の「営業 課員」を名前引きしている。
  従業員数は固定アカウント表の長さと暗黙に結合しており、値の外出しだけでは不正値を
  与えられる口を開けたことになる。
  ガードを `main()` ではなくモジュール評価時に置いたのは、`main()` が先頭で全テーブルを
  `deleteMany` するため、そこで検証すると「DB を全消ししてから設定ミスで落ちる」最悪の
  順序になるため

## 4. `.env.production.example` を更新できていない

- **元の計画**: Step 3 で `SEED_DEFAULT_PASSWORD` / `SEED_TOTAL_EMPLOYEES` のキー名を追記する
- **実際の実装**: **未実施**
- **理由**: このファイルは権限設定により読み書きが拒否されており（Bash・Read とも）、
  エージェントからは編集できなかった。迂回はしていない。追記内容は PR 本文に記載した

## 5. Step 5 の検証は `.env.production` を作らずに実施した

- **元の計画**: `--env-file .env.production` で一式を起動して検証する
- **実際の実装**: 環境変数をシェルから直接渡し `--env-file /dev/null` で起動して検証した
- **理由**: 上記 4 と同じく `.env*` の作成が権限で拒否されるため。compose の変数解決は
  プロセス環境からも行われるので、検証内容としては等価

## 6. 所要時間の想定が実測と外れていた

- **元の計画**: 設計判断 #6 で「2000 件は 1 件ずつ await するため所要時間が件数に線形」とし、
  インスタンスサイズに応じて減らす余地を残す目的で env 化した
- **実際の実装**: 方針は変更なし。ただし CLAUDE.md の記述を実測値に差し替えた
- **理由**: ローカル実測で 2000 件の seed 全体が 12 秒（従業員生成部分は 7.8 秒）だった。
  線形である点は正しいが「数分かかる」という記述は誤りだったため修正した。
  env 化そのものは EC2 のインスタンスサイズ未定という理由で引き続き有効
