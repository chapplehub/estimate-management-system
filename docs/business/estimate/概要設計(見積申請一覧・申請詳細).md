# 概要設計(見積申請一覧・申請詳細)

> 本書は **見積申請一覧・見積申請詳細** の画面概要設計である（issue #566）。
> BE（申請・承認のドメイン/データモデル）は [システム設計書(申請)](./システム設計書(申請).md) を前提とする。
> 本書は概要設計であり、DTO・クエリ・UI コンポーネントの詳細設計と実装は後続 issue で行う。
> 用語は [CONTEXT.md](../../../CONTEXT.md) の正準語に従う（特に: 申請 / バリエーション申請状態 / 最新申請 / 承認待ち役割 / 承認免除）。

## 1. 目的と位置づけ

見積申請一覧は **全社台帳** である。全社員が全申請を検索・閲覧でき、検索条件によって次の 2 用途を吸収する（専用画面は分けない）。

- **承認者のワークリスト**: 「申請状態＝申請中 × 承認待ち役割＝自分の役割」で自分が処理すべき申請を抽出し、詳細へ遷移して承認・差戻を行う
- **申請者の追跡**: 「申請者名＝自分」で自分の申請の進行を確認し、必要なら詳細で取下を行う

見積申請詳細は、あるバリエーションの **申請の全容（最新申請・過去履歴・免除記録）を閲覧し、承認・差戻・取下を実行する場所** である。承認・差戻・取下のコマンドは BE 実装済み（`ApproveStep` / `RejectStep` / `WithdrawApplication`）だが UI が存在しないため、本画面がその操作場所となる。

### 操作を見積詳細でなく申請詳細に置く理由

- ワークリスト動線（一覧→詳細→処理）が一画面で閉じる。詳細が閲覧専用だと、承認者は内容確認後に見積詳細へ移動し直すことになり動線が切れる
- 見積詳細は「見積を編集する担当者」の画面であり、申請ボタン（自分の案件を出す）はその文脈に合う。一方、承認・差戻は他人の申請を裁く行為で、承認チェーンの進行・過去の差戻コメントという申請固有の文脈を要する。その文脈が揃うのは申請詳細のみ
- 取下（申請者本人の操作）も「チェーンがどこまで進んだか」を見て判断するため同じ場所でよい

## 2. 見積申請一覧

- ルート: `/estimate-applications`（`(features)` 直下・フラット。ADR-0053 のテーブル分離と同じ切り方で、将来の価格申請一覧と画面レベルでも分離する）
- 画面名: 「見積申請一覧」（「見積申請」は将来の価格申請と区別する修飾語。CONTEXT.md「申請」の項を参照）

### 2.1 行単位: バリエーション単位（最新申請で代表）

一覧の 1 行は **申請または承認免除を持つバリエーション** 1 件。行の状態・申請者・申請日時は **最新申請**（attempt 最大の申請）から導出する。未申請バリエーションは母集合に含めない（それは見積一覧の関心）。

採用理由（申請単位＝1申請1行 案とのトレードオフ）:

1. **検索の意味が実務と一致する**。申請単位だと「申請状態＝差戻」の検索が、再申請済みで承認済みになった案件の古い差戻申請までヒットする。承認者・申請者のどちらの用途でも知りたいのは「今、差戻状態で対応が必要なバリエーション」であり、バリエーション単位ならこれが自然に成立する
2. **既存概念の再利用**。バリエーション申請状態（#559 実装済み）をそのまま行状態に使え、見積詳細のバッジと一覧が同じ語彙・同じ導出規則で揃う
3. **役割分担の明確化**。「一覧は現在（最新申請）、詳細は履歴（全 attempt）」の原則で、attempt の履歴を一覧に行として散らばらせない

見積単位は不採用: 申請の対象はバリエーションであり、1 見積内で「あるバリは承認済・別のバリは未申請」が普通に起きるため、畳むと台帳情報が失われる。

### 2.2 承認免除を含める理由

免除バリエーションは状態「承認不要」の行として一覧に含める。

1. 操作者から見れば同じ申請アクションの結果である（`SubmitApplicationCommand` の結果 union は `ApplicationSubmitted | ApprovalExempted`）。免除案件だけ台帳から引けないのは台帳として欠陥
2. 免除は「記録が残る」ことに意味がある設計（ADR-0054）であり、記録の参照手段が見積詳細のバッジしかない状態を解消する
3. 状態フィルタが「バリエーション申請状態」の語彙（未申請を除く 5 値）と完全に揃う
4. ワークリスト検索（承認待ち役割指定）には免除行はヒットしないため、ノイズにならない

### 2.3 検索条件（7 項目）

| 条件 | 型 | 主な用途 |
|---|---|---|
| 見積番号 | テキスト・部分一致 | 台帳（案件から引く） |
| 得意先名 | テキスト・部分一致 | 台帳 |
| 納品先名 | テキスト・部分一致 | 台帳 |
| 申請状態 | select（申請中/差戻/取下/承認済/承認不要） | 全用途の軸 |
| 申請者名 | テキスト・部分一致 | 申請者の追跡 |
| 承認待ち役割 | select（役割マスタ） | 承認者ワークリスト |
| 申請日 | 期間（from–to） | 台帳・監査 |

- 「承認待ち役割」は申請中の行にのみ意味を持つ導出値（差戻・承認行を持たない最小順序ステップの役割。ADR-0058 の導出規則）。指定時は暗黙に申請中のみヒットする
- 「自分が承認待ち」トグル（ログイン社員の所属役割で絞るショートカット）は本 issue では持たない。「承認待ち役割 ∈ 自分の所属役割」の糖衣であり、後続で追加可能

### 2.4 一覧列（10 列）とソート

| 列 | 内容 |
|---|---|
| 見積番号 | 案件の識別子 |
| バリエーション | `variationNumber`（バリエーションは名称を持たない） |
| 得意先 | 検索条件と対応 |
| 納品先 | 検索条件と対応 |
| 提出区分 | 得意先宛/納品先宛 |
| 金額 | 税込合計（`finalTotal`）。承認段階を決める基準金額（ADR-0055） |
| 申請状態 | バリエーション申請状態バッジ（見積詳細と同じ表示） |
| 承認待ち役割 | 申請中のみ値を持ち、他状態は「—」 |
| 申請者 | 最新申請の申請者。免除行は免除実施者 |
| 申請日時 | 最新申請の発生日時。免除行は免除日時 |

- デフォルトソート: 申請日時の降順（台帳として新しい動きが上）
- 取得件数: 既存一覧と同じ `LIST_FETCH_LIMIT` 方式（ページングなし）
- 行のナビゲーション: 見積申請詳細へ遷移。見積詳細へのリンクは一覧には持たせず、申請詳細内のリンクに一本化する

## 3. 見積申請詳細

- ルート: `/estimate-applications/[estimateNumber]/[variationNumber]`（バリエーションの自然キー。既存の `estimates/[estimateNumber]` と同じく業務キーを URL に使う。免除のみのバリエーションも同じキーで表せる）
- 画面名: 「見積申請詳細」

### 3.1 表示ブロック

1. **バリエーション要約ヘッダ**: 見積番号（見積詳細へのリンク）・バリエーション番号・得意先/納品先・提出区分・税込合計金額・申請状態バッジ。明細の全内容は見積詳細に委ね、本画面には複製しない
2. **最新申請の承認チェーン**: 申請者・申請日時・attempt・最終承認役職、各ステップ（順序・役割・導出状態・承認者/差戻者・発生日時・差戻コメント）
3. **過去の申請履歴**: attempt 順に、過去の各申請を承認チェーン込みで表示（差戻コメント・取下記録を含む）
4. **免除バリエーションの場合**: チェーンの代わりに免除記録（理由・実施者・日時）
5. **操作**: 承認・差戻・取下ボタン（§4 の出し分けに従う）

### 3.2 過去申請を承認チェーン込みで表示する理由

1. 再申請の審査には前回の差戻コメントが必須。差戻理由は必須項目（ADR-0058: `comment` NOT NULL・default なし）として書かせており、次の審査で読まれる場所が本画面以外にない
2. ドメイン設計が「旧申請は履歴として残す」（CONTEXT.md「申請」）としており、残した履歴の参照画面が本画面
3. 「attempt 1: 差戻」の 1 行要約では、どのステップまで進み誰が差し戻したかが分からない。折りたたみ等の UI 詳細は後続 issue で決める

## 4. 権限と操作の出し分け

- **閲覧は全社員・全申請**。既存一覧（見積・商品・得意先など）と同じ全件台帳パターン
- **操作ボタンは資格者にのみ表示**:
  - 承認・差戻: 状態＝申請中 かつ ログイン社員が承認待ちステップの役割メンバーであるときのみ
  - 取下: 状態＝申請中 かつ ログイン社員が申請者本人であるときのみ
- **操作可否は BE が読み取り DTO で供給**する（`canApprove` / `canReject` / `canWithdraw` 相当）。#562 の `canApply` と同じパターンで、FE は役割メンバーシップ判定を複製しない
- **最終防衛は BE**。表示制御をすり抜けても実装済みコマンド側ガード（役割メンバー検証・本人性検証・楽観ロック）が拒否する

## 5. スコープ外（後続 issue）

- 過去申請履歴の折りたたみ等の UI 詳細
