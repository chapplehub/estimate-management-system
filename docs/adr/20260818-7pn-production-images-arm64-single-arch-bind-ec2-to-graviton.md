# ADR-20260818-7pn: 本番イメージは arm64 単一アーキテクチャでビルドし、EC2 を Graviton に拘束する

| 項目 | 値 |
|---|---|
| ステータス | 採用 |
| 起票日 | 2026-08-18 |
| 最終更新日 | 2026-08-18 |

## コンテキスト

Issue #763 で、プロダクション用イメージ（`Dockerfile` の `runner` / `migrate`）を GitHub Actions でビルドし GHCR へ push するワークフローを整備する。ここで CPU アーキテクチャを決める必要がある。ビルドするアーキテクチャはデプロイ先 EC2 のインスタンスタイプ（Graviton = arm64 か、従来の x86_64 か）と一体の決定であり、後続の EC2 構築イシューを拘束するため、ワークフロー設計に先立って確定させる（Issue #763 の未決事項筆頭）。

前提となる事実:

- 本リポジトリは **public** であり、GitHub Actions の arm64 ホステッドランナー（`ubuntu-24.04-arm`）が**無料**で使える。Issue 起票時に懸念されていた「QEMU クロスビルド（低速）か有料 arm64 ランナーか」の二択は、public リポジトリでは存在しない。
- EC2 は Graviton（t4g 系）が同等スペックの x86（t3/t3a 系）より約 10〜20% 安く、常時起動の本番インスタンスでは差額が恒常的に効く。
- スタックに arm64 の障害は無い: Prisma は Rust エンジンレス構成（`Dockerfile` 前提コメント）、`node:24-slim` / `postgres:16.14-trixie` / `nginx:1.28.0-alpine` はいずれも arm64 マニフェストを提供する。
- 開発機は WSL2（x86_64）。ローカルでの本番構成検証は「`docker build` でローカルタグを作り `APP_IMAGE` / `MIGRATE_IMAGE` に指定する」運用が確立済み（CLAUDE.md）で、GHCR の本番イメージをローカルへ pull する運用は存在しない。

## 検討した選択肢

### A. x86_64 単一（不採用）

GitHub Actions の標準ランナー（x86_64）でネイティブビルドし、EC2 も x86 系（t3/t3a）にする。

- 利点: 開発機（WSL2 = x86_64）と本番が同一アーキテクチャになり、GHCR の本番イメージそのものをローカルで pull して検証できる。
- 欠点: EC2 の時間単価が Graviton より高く、常時起動で差額を払い続ける。「本番イメージをローカルで pull 検証する」という利点は、確立済みのローカルビルド検証運用では使われない。

### B. arm64 単一（採用）

`ubuntu-24.04-arm` ランナーでネイティブビルドし、EC2 は Graviton（t4g 系）にする。

- 利点: EC2 費用が最安。public リポジトリのため arm64 ランナーは無料で、ネイティブビルドなので速度ペナルティも無い。
- 欠点: EC2 インスタンス選定が Graviton 系に固定される。GHCR のイメージは開発機（x86_64）で直接は動かない（ローカル検証はローカルビルドで代替する前提）。

### C. multi-arch（amd64 + arm64）（不採用）

buildx で両アーキテクチャのマニフェストを発行する。

- 利点: デプロイ先・検証環境のアーキテクチャを問わなくなる。
- 欠点: ビルド時間・ジョブ構成が倍になる（arm64 ネイティブ + amd64 の 2 ビルド + manifest 統合）。amd64 イメージの消費者が現存しない（ローカル検証はローカルビルドで足りる）ため、恒常コストだけ払って得るものが無い。

## 決定

本番イメージは arm64 単一アーキテクチャでビルド・push し、デプロイ先 EC2 は Graviton（t4g 系）を前提とする。

## 根拠

- 決定コストの非対称性: arm64 化の追加コストは public リポジトリではゼロ（無料ネイティブランナー・技術的障害なし）に対し、リターン（EC2 費用 10〜20% 減）は常時起動で恒常的に効く。
- A の唯一の実益「本番イメージのローカル pull 検証」は、確立済みのローカルビルド検証運用と重複しており、需要が現存しない。
- C は「消費者のいないイメージ」のために CI 構成を倍に複雑化する。必要になった時点（例: x86 環境へのデプロイ先追加）で buildx のプラットフォーム追加として後付けできる。

## 影響

- 後続の EC2 構築イシューでは、インスタンスタイプを Graviton（t4g 系）から選ぶこと。x86 系を選ぶ場合は本 ADR の差替（ワークフローのランナー・タグ運用の変更）が必要になる。
- GHCR 上のイメージは x86_64 環境（開発機の WSL2 を含む）ではネイティブ実行できない。ローカルでの本番構成検証は、従来どおりローカルビルドのタグを `APP_IMAGE` / `MIGRATE_IMAGE` に指定して行う（CLAUDE.md の手順）。
- イメージビルドを行うワークフローのランナーは `ubuntu-24.04-arm` を使う。リポジトリを private 化すると arm64 ランナーが課金対象になるため、可視性変更時は本決定のコスト前提が崩れることに注意。
