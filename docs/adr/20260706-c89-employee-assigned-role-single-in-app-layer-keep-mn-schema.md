# ADR-20260706-c89: 従業員の担当役割は多対多スキーマ（EmployeeRole）を維持しつつ、アプリ層で高々1件に制約する

| 項目 | 値 |
|---|---|
| ステータス | 採用 |
| 起票日 | 2026-07-06 |
| 最終更新日 | 2026-07-06 |

## コンテキスト

#565 で従業員の担当役割（→CONTEXT「担当役割」）を登録・更新画面から設定できるようにする。業務方針として、現時点では1従業員が持つ担当役割は**高々1つ**に限定する。

一方、既存スキーマの `EmployeeRole` は複合PK `(employeeId, roleId)` の**多対多結合表**で、1従業員がN役割を持てる構造になっている。承認側の読み取り（`RoleQueryService.findRoleIdsWithMembers` / `hasMember`）も、この多対多を前提に `employeeRole` を引いて「承認者メンバーの母集合」「自己承認可否」を判定している。

「1従業員 = 高々1担当役割」という業務ルールを **DBスキーマで表現するか、アプリ層で表現するか** を決める必要がある。

## 検討した選択肢

### A. 多対多スキーマを維持し、アプリ層（Employee 集約）で高々1件に制約する（採用）

`EmployeeRole` の多対多結合表はそのまま残し、`Employee` 集約が担当役割を単一の `RoleId | null` として保持する。Repository は保存時に `EmployeeRole` 行を 0/1 件へ同期し、「高々1件」を集約の不変条件として守る。DB には部分ユニーク等のバックストップを張らない。

### B. スキーマを単一FK `Employee.roleId` に作り替えてモデルと一致させる（不採用）

`EmployeeRole` 結合表を廃し、`Employee` に単一の `roleId` 列（+FK）を持たせる。「高々1件」を DB のカラム構造そのもので表現する。

## 決定

**選択肢 A を採用する。** 多対多スキーマ（`EmployeeRole`）を維持したまま、担当役割の「高々1件」制約を Employee 集約のアプリ層不変条件として強制する。

## 根拠

- **移行コストの非対称性**。単一FK化（B）は、既に多対多前提で `employeeRole` を引く承認クエリ群（`findRoleIdsWithMembers` / `hasMember`）まで巻き込む重い migration になる。対して A の「アプリ層で1件に絞る」は Employee 集約と Repository の書き込みガードだけで閉じ、承認サブドメインを無改修に保てる。
- **非可逆性の回避**。「1役割」は現時点の業務簡約であり、将来「兼務を許す」方向へ緩む可能性がある。多対多 → 単一FK は **lossy（非可逆）** だが、多対多のまま1件運用（A）なら、緩和時はアプリ層のガードを外すだけで済みスキーマ移行が要らない。
- **バックストップをアプリ層へ寄せる既存方針との一貫**。「1見積1前進」のDB部分ユニークを廃してアプリ層（見積アグリゲートの楽観ロック）へ一元化した ADR-0058 と同型。整合性の担保点をアプリ層に集約する流儀に沿う。
- **集約の所有分離**。`EmployeeRole` の**書き込み**は Employee 集約が所有し、role サブドメインは**読み取り（メンバー判定）だけ**する、という所有分離が保てる。

## 影響

- 将来の読者に「なぜ多対多表なのに集約は単一役割なのか」という驚きが生じるが、本 ADR がその根拠（移行コスト非対称・将来の兼務緩和に対する非可逆性）を残す。
- DB は「高々1件」を強制しない（部分ユニーク等を張らない）。整合性は Employee 集約の不変条件に一元化し、並行更新の直列化は `Employee.version` の楽観ロック（ADR-0039）に委ねる。
- 将来、兼務（N役割）を許す場合は、集約の表現（単一 `RoleId` → 配列）とガード撤廃で対応でき、スキーマ移行は不要。
