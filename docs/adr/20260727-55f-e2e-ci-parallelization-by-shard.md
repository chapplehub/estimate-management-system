# ADR-20260727-55f: E2E の CI 並列化は shard 分割で行い、shard 内は直列実行を維持する

| 項目 | 値 |
|---|---|
| ステータス | 採用 |
| 起票日 | 2026-07-27 |
| 最終更新日 | 2026-07-27 |

## コンテキスト

E2E（Playwright）が CI のボトルネックになっている。直近の成功 run は約 9 分 33 秒で、内訳は準備一式（checkout 〜 Playwright install）が 68 秒、`Run Playwright tests` が 495 秒。spec は 46 ファイル / 370 件あり、機能追加のたびに線形に伸びる。PR のフィードバックループが 10 分近くに張り付き、レビュー・修正のサイクルが目に見えて遅くなっている。

`playwright.config.ts` は CI で `workers: 1` 固定のため、`fullyParallel: true` が実質効いていない。並列化の余地はあるが、**手段が複数あり、どれを選ぶかで既存テスト資産への影響が大きく異なる**ため、方式選択の判断が必要になった。

本 ADR は E2E テスト基盤の系譜の 3 本目にあたる。

- ADR-0012: Prisma 7 の ESM/CJS 不整合によりテスト内から直接 DB 操作ができないため、データ管理を `test.describe.serial` による直列化で解決すると決めた
- ADR-0020: その上に「DB 状態変化あり = serial + 新規データ / なし = 並列 + シード」の 4 分類を敷いた
- 本 ADR: **CI 上で E2E をどう並列に流すか**を決める

## 検討した選択肢

### A. shard 内の `workers` を引き上げる（不採用）

`workers: 1` を 2〜4 に上げる。設定変更 1 行で済み、ジョブ数も増えないため固定オーバーヘッドの重複がない。

しかし shard を切らずに `workers` だけ上げると、**同一 DB を複数ブラウザが同時に操作する**。実在する衝突例:

- `src/app/(features)/customers/customers-list.e2e.ts:73` — 郵便番号 `1000001` での検索結果を `toHaveCount(1)` で検証
- `src/app/(features)/customers/customers-crud.e2e.ts:31` — **同じ郵便番号 `1000001`** で `CUST901` を作成

現在は直列のため CRUD の「作成 → 削除」が閉じてから list が走り成立している。並列化すると作成〜削除の窓で list が 2 件を観測して落ちる。

`toHaveCount` は全体で **100 箇所 / 22 ファイル**にあり、同種の暗黙の前提が他にも潜んでいる前提で判断すべき。採用するには 100 箇所の前提監査と、必要なら ADR-0020 のデータ戦略そのものの再設計を伴う。

### B. shard 分割（採用）

`playwright test --shard=i/N` を GitHub Actions の matrix で N 並列に流す。各 matrix ジョブは独立したランナー VM に載るため、**postgres service・Next サーバー・`playwright/.auth/*.json` がすべてジョブごとに分離される**。共有リソースが存在しないため、既存テストを 1 行も変えずに並列化できる。

分割の最小単位を `playwright test --list --shard=i/4` で実測した。

| 単位 | 挙動 |
|---|---|
| `test.describe.serial` グループ | 丸ごと 1 単位。**分断されない** |
| serial の外にある独立テスト | 1 件が 1 単位 |

`customers-crud.e2e.ts`（12 件）は shard1 / shard2 に散ったが、切れ目は必ずグループの外側に入った。

```
shard1 ← serial「ライフサイクル」                 作成 → 詳細 → 更新 → 削除（4 件が丸ごと）
shard2 ← serial「ステータス管理」                 作成 → 無効化 → 有効化 → 削除（4 件が丸ごと）
         独立テスト 2 件（納品先あり削除不可 / コード重複）
         serial「一般ユーザーも作成・削除できる」  （2 件が丸ごと）
```

`delivery-locations-list.e2e.ts` では独立テスト 1 件だけが切り離された。**ADR-0012 が敷いた `describe.serial` が、そのまま shard 境界の保護単位として機能する。**

shard を跨ぐ暗黙のデータ依存も調査し、存在しないことを確認した。

- 複数ファイルで共有される識別子は `C902` / `C903` / `D904` の 3 つのみで、いずれも `seed-e2e.ts` 定義。各 shard が自前で `e2e:seed` を流すため全 shard に等しく存在する
- テストが生成する 901 帯のデータは、すべて単一ファイル内で閉じている
- 採番結果（見積番号など）を固定値で検証している箇所はゼロ。shard ごとに採番系列が変わっても壊れない

### C. `webServer` を production build 起動に切り替える（不採用）

`pnpm dev`（`next dev`）をやめ `next build` + `next start` にすれば、JIT コンパイルが消え最適化ビルドで走るためテスト自体が速くなる。#644 の解決によりビルド時 DB 到達の問題は解消済みで、技術的な障害はない。

しかし **shard 化とは競合関係にある**。shard 化はテスト実行時間を N で割るが、`next build` は N で割れない —— shard ごとに実行すれば N 倍に増え、前段の単独ジョブでやれば直列に前置される。一方 dev server にはビルドステップがなく、JIT コンパイルのコストはテスト実行時間の内側にあるため、各 shard が自分の触るルートしかコンパイルせず**コンパイルコストも N でおおむね割れる**。

損益分岐は、ビルド時間 B について次で表される。

```
B < (T_dev − T_prod) / N
```

`T_dev = 495 秒`、production が E2E を 25% 速くすると仮定して `T_prod ≈ 370 秒`、`N = 4` なら **B < 31 秒**。Next 16 + React Compiler 有効 + 39 ルートでこれは非現実的。

「ビルド 1 回 → `.next` を artifact で各 shard に配る」設計はさらに不利で、準備ステップ（68 秒）が 1 段余計に直列で積まれるぶん分岐点が負になり、**B がいくら小さくても選択肢 B に勝てない**。

### D. テストを shard へ手動で振り分ける（不採用）

Playwright 1.58 の shard 分割は**件数ベースで実行時間ベースではない**（時間ベース分割の機能は存在しない）。project 分割やタグで重いテストを手で振り分ければ、実行時間を均せる。

実測の件数分布は 96 / 92 / 94 / 94（4 分割）で件数の偏りはないが、見積系を含む shard3・shard4 が実行時間で上振れする可能性はある。ただし偏りが平均の 1.4 倍あっても wall clock は 4 分 01 秒で、完全均等（3 分 12 秒）との差は **49 秒**にとどまる。この 49 秒のために「テストを追加するたびに再バランスする」恒久的な保守負債を負うのは割に合わない。

さらに、偏りへの対処としては**手動振り分けより shard 数の引き上げの方が優れている** —— 最重 shard の中身自体が減るため、保守コストゼロで同じ効果が得られる。

## 決定

E2E の CI 並列化は **`--shard` による分割（DB・サーバーごと分離）で行い、shard 内の `workers` は 1 に据え置く**。

## 根拠

- **既存テスト資産を改修せずに並列化できる**: shard 間は postgres・Next サーバー・認証ストレージがすべて分離されるため、共有リソース由来の競合が構造的に発生しない。選択肢 A が必要とする 100 箇所の前提監査を回避できる。
- **ADR-0012 の serial 戦略が保護境界としてそのまま効く**: 分割の最小単位が `describe.serial` グループであることを実測で確認済み。既存の直列化設計を壊さない。
- **shard 化は dev server を相対的に有利にする**: 選択肢 C が不利になる理由（ビルドが N で割れない）は、shard 化を選んだ時点で確定する。両者は補完ではなく競合であり、片方を選べばもう片方の価値が下がる。
- **偏りへの調整レバーが保守コストゼロで手に入る**: shard 数は matrix の配列 1 行で可変。選択肢 D の手動振り分けは最後の手段として残す。

## 影響

- shard 数は**可変パラメータ**として扱う。初期値は 4（準備 68 秒の重複により短縮率が逓減し、4 → 6 の追加短縮は約 41 秒にとどまるため）。実測を見て見直す。
- `pnpm install` / `db:generate` / `migrate deploy` / `e2e:seed` / `playwright install` / dev server 起動という準備一式が **shard 数だけ重複する**。分割数を増やすほど短縮率は逓減する。
- `dependencies: ["setup"]` により `auth.setup.ts` の 2 件が**全 shard で実行される**。shard ごとに別プロセス・別サーバーで `playwright/.auth/*.json` を生成する必要があるため、仕様どおりの挙動。
- レポートが shard ごとに分かれるため、`blob` reporter + `merge-reports` による統合が必要になる。`merge-reports` は**テスト失敗時も exit 0 で終わる**ため、統合ジョブには shard の結果を集約して失敗を伝播させる責務を明示的に持たせる。持たせないと「4 shard 中 1 つが赤なのに統合ジョブは緑」が常態化する。
- GitHub の **「Re-run failed jobs」（失敗したジョブのみ再実行）が使えなくなる**。`actions/upload-artifact` は v4 以降、同一 run 内で同名 artifact を二度アップロードできず、artifact は再実行の attempt をまたいで保持されるため。再実行は「Re-run all jobs」を前提とする（全 shard が並列で走り直すため、全ジョブ再実行でもウォールクロックは 1 shard 分にとどまる）。shard 化する前は artifact が 1 個かつ再実行がジョブ 1 本＝全体だったため、この制約は存在しなかった。
- **今後 `workers` を引き上げる場合**、shard 内で同一 DB を複数ブラウザが叩く状態に戻るため、`toHaveCount` 100 箇所 / 22 ファイルの前提監査と ADR-0020 のデータ戦略の再検討が前提になる。本 ADR はそれを別スコープとして切り離している。
- production build 化は本 ADR で不採用とした。ただし #643 が CI に `build` ジョブを追加すれば実際のビルド時間が観測できる。それが 30 秒台で、かつ shard 化後の実測で dev のコンパイル待ちが目立つ場合に限り、再検討の余地がある。
- serial チェーン**中盤**の失敗に対しては `retries` が構造的に効かない。Playwright はグループを先頭から再実行するが、1 回目の「作成」が残したレコードで重複エラーになるため。これは本 ADR のスコープ外の既存課題であり（ADR-0012 の「シリアルチェーン途中の失敗でデータが残留した場合は再シードが必要」と同根）、shard 化によって新たに生じるものではない。
