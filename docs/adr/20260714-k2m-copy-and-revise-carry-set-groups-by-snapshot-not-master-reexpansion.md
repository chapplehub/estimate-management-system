# ADR-20260714-k2m: 複製・改訂はセット群を群ごとスナップショット複写する（マスタから再展開しない）

| 項目 | 値 |

| ステータス | 採用 |
| 起票日 | 2026-07-14 |
| 最終更新日 | 2026-07-14 |

## コンテキスト

見積複製（C6 `EstimateDuplicationService.toCopiedDescriptor`）と得意先改訂（C7 `Estimate.reviseForCustomer`）が、複製元／改訂元バリエーションのセット群（ADR-0047）を引き継いでいなかった（Issue #602。PR #600 の自動レビューで検出）。

原因は「取りこぼし」であり、設計意図ではない。根拠は、業務仕様書 §5.3「引き継ぎ項目」がセット群導入前の記述のままであること、ADR-0047 の「影響」節が波及先として C1/C4（作成・内容更新）しか挙げず C6/C7 を落としていること。

ADR-0047 は「価格付き末端行 1 表 ＋ 薄いセット群衛星」を選び、`EstimateVariation._items` に**通常明細と構成明細を同居**させた。一方、生成側の記述子（`EstimateVariationDescriptor`）は `items`（通常明細）と `setGroups[].components`（構成明細）に**分離**した入れ子形を要求する。複製・改訂はこの「平坦 → 入れ子」の組み直しを行わず `source.items` を丸ごと `items` に流し込んでいたため、構成明細がバラの通常明細として並び、群が消えていた。

修正にあたり「複製先・改訂先のセット構成を何から作るか」を決める必要がある。単価は既に「マスタから再解決」する（#431・ADR-0064）ため、構造も同様にマスタ追従させるという選択肢が自然に浮かぶ。

## 検討した選択肢

### A. 群ごとスナップショット複写（採用）

群の `productId` / `itemName` / `unit` / 顧客メモ / 社内メモと、構成明細の並び（`sortOrder`）・品目・数量を元からそのまま複写する。構成明細も価格付き末端行なので、通常明細と**同一の変換規則**（単価は再解決／掛率は継承／固定値引はクリア／改訂では `deliveryPrice` スナップショットを付与）を適用する。セット群自体は価格を持たない（→価格保守対象商品ではない）ため、群の `productId` を単価解決の対象に入れない。

### B. セット商品マスタから再展開（不採用）

複製先・改訂先の生成時に、`SetProductComponent`（セット構成マスタ）の現在値から構成明細を作り直す。

## 決定

複製・改訂ではセット群を**群ごとスナップショット複写**し、セット商品マスタから再展開しない（A を採用）。

これにより、単価再解決を伴う生成（見積複製・得意先改訂）の規則は次の単一原則に統合される:

> **構造（群の存在・構成・スナップショット属性・メモ）は複写。率（掛率）は継承。絶対額（固定値引）はクリア。単価のみ再解決。**

## 根拠

- **改訂では再展開が原理的に不可能。** 改訂先は行構成固定（ADR-0046）・数量固定（ADR-0060）で、改訂元と明細が 1:1 に対応していなければ粗利スナップショット `deliveryPrice`（§8.4）が成立しない。マスタのセット構成が変わっていれば行数が変わり、粗利比較の基準が崩れる。
- **複製だけ再展開すると非対称になる。** 通常明細は `itemName`・数量すらスナップショット複写でマスタ追従しない。セット構成だけを追従させる根拠がない。
- **集約越え依存を C6/C7 に持ち込まない。** 再展開には Product 集約（`SetProductComponent`）が必要で、ADR-0052 の「アプリ層が事実を集めメソッド引数で渡す」経路を複製・改訂にも新設することになる。単価解決のために既に価格決定を通しているが、そこへ構成解決という別の集約越えを重ねる対価に見合わない。
- **群メモは複写でなければ復旧不能。** 固定値引をクリアできた根拠（ADR-20260714-pv8）は「改訂先で入れ直せる＝入れ忘れは安全側の失敗」だった。セット群のメモにはこの前提が成立しない——群メモを更新できるのは C4 `UpdateVariation`（`replaceContent` 全置換）だけで、改訂先は行構成固定によりその経路が塞がれている（`UpdateVariationMemosCommand` はバリ単位メモと明細単位メモしか扱わず、`EstimateSetGroup` に memo の setter は存在しない）。クリアすれば改訂先の群メモは永久に空になる。メモは金額に効かない注記（ADR-0059）であり、単価再解決との整合も壊さない。
- **構成明細は通常明細と同型ゆえ変換規則を割らずに済む。** ADR-0047 が「通常明細と構成明細は列構成が完全一致する同じ価格付き末端行」と決めたため、単価再解決・値引クリア・掛率継承・`deliveryPrice` 付与をそのまま構成明細へ適用できる。

### 不採用理由まとめ

- **B（マスタ再展開）**: 改訂では 1:1 行対応が崩れて粗利スナップショットが成立しない。複製のみに適用しても通常明細のスナップショット複写と非対称になり、Product 集約への新たな依存を C6/C7 に持ち込む。

## 影響

- **「平坦 ⇔ 入れ子」の変換点を `EstimateVariation` に一本化する。** 通常明細と構成明細の仕分けは `_items`（実体）と `_setGroups`（所属 id）の両方を持つ `EstimateVariation` にしかできない。読み取り API（`lineStructure`）を 1 つ設け、複製・改訂はこれを起点に自分の変換規則を適用する。変換関数そのものは統合しない——複製はドメインサービス（集約外）なので記述子を作り、改訂は集約内なので `EstimateItem` / `EstimateSetGroup` を直接 `create` する。加えて `EstimateFactory` が `Estimate` を import しているため、`Estimate` 側から `EstimateFactory` を呼ぶ道は循環参照で塞がっている。共通化の上限は「仕分け」である。
- **群 ID は新採番**され、群の `memberItemIds` は**新しく生成された**構成明細の id を指す（構成明細を先に `create` して id を確定させてから群へ配線する。`EstimateFactory.buildSetGroups` と同じ手順を改訂側でも踏む）。
- **表示位置・金額は追加対応不要。** 群の金額は構成明細の合計、表示位置は最小 `sortOrder` から導出される（ADR-0047）。`sortOrder` を複写すれば群の位置も構成明細の連続配置も復元される。
- **既存データの修復は行わない。** セット群は金額計算に関与せず（`computeTotals` は `_items` のみ集計）、構成明細の行自体は正しく複写されていたため、被害は表示のグルーピングと群見出しに限られ、合計金額・税額・粗利スナップショットは正しい。加えて複製先は生成後に自由編集可能（行の追加・削除・並べ替え）なので、複製系譜から元の群構成を機械的に当てはめると編集後の行と食い違って壊しかねない。壊れたバリエーションは再改訂・再複製で健全な状態を得る。
- **型では防げない取りこぼしである。** `EstimateVariationDescriptor.setGroups` を必須化しても、`items: source.items, setGroups: []` と書けば型は通り同じ症状になる。真因は「渡し忘れ」ではなく「組み直し忘れ」であり、同型の要素（通常明細・構成明細）が 1 配列に同居する以上、型は「どちらか」を語れない。防御は型ではなく `lineStructure` という唯一の変換点で入れる。
- **将来「複製時は最新のセット構成に追従したい」要件が出た場合**、本 ADR の棄却理由がそのまま制約になる。複製先だけ追従させると通常明細のスナップショットと非対称になり、改訂には適用できない（1:1 行対応）。追従を選ぶなら、スナップショット複写との混在した母集団が生まれることを受け入れる設計が別途必要。
