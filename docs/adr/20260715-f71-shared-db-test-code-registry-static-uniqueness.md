# ADR-20260715-f71: 共有DB単体テストのコード割当をコードキー・レジストリで静的に一意化する

| 項目 | 値 |

## コンテキスト

DB依存の単体テスト（vitest）は、`.env.unit` の**単一の共有テストDB**上で、テストファイルを**別ワーカーで並列実行**する（ADR-0012 によりテスト内で Prisma を直接使わず実DBに対して検証する）。各テストは `beforeEach`/`afterEach` で自分の使うコード（`roleCd` 等）に一致する行を削除してからデータを組む。

このため、**2つのテストファイルが同じコードを使う**と、共有DB上で相互に干渉して確率的（flaky）に落ちる。#608 では次が起きていた。

- `UpdateRoleCommand.test.ts` と `PrismaEmployeeQueryService.roleNames.test.ts` が**同一の役割コード `ROLE971-973`** を共有。
- 一方の `beforeEach` cleanup が、他方が使用中の行を削除 → ①role生成の一意制約違反(P2002)／②期待値の null 化／③`NotFoundEntityError` として顕現。

これは新しい問題ではない。#61→#62、#327、承認系#493 と、同じ「並列テストのデータ分離」問題が繰り返し発生してきた。従来の対策は**人間の規律に依存**しており、role/employee 空間では実際に `EMP990710/711` も別ファイル間で二重占有しているなど、規律が破綻していた。

隔離に必要な不変条件は明確である：**1コード = 高々1所有テストファイル**（同一ファイル内の複数ケースは同ワーカー直列なので共有可）。問題は、この不変条件を**何が担保するか**である。

## 検討した選択肢

### A. コードキーのレジストリ ＋ TS1117 による静的一意検証（採用）

コード空間（ユニークカラム）ごとに1つのレジストリファイルを `src/server/__tests__/helpers/test-codes/` に置き、**コード文字列をキー**にした `as const` マップで所有者・用途を宣言する。

```ts
export const ROLE_TEST_CODES = {
  ROLE971: { owner: "employee.roleNames", use: "assignedRole" },
  ROLE972: { owner: "employee.roleNames", use: "seniorRole" },
  ROLE973: { owner: "employee.roleNames", use: "leafRole" },
} as const;
```

同じコードを二度割り当てると**オブジェクトリテラルの重複キー**になり、TypeScript が **TS1117**（`An object literal cannot have multiple properties with the same name`）でコンパイル時に弾く。pre-push の `tsc --noEmit` とエディタで、**DBを一切触らず**衝突が検出される。消費側は import 時に1回だけ構築する派生索引（`owner → { use: code }`）を分割代入で引く。

### B. 承認系(#493)の所有者キー ＋ ランタイムのガードテスト（不採用）

`approvalTestBands.ts` は「所有者キー → コード配列」で宣言し、一意性は別のガードテスト（全値をフラット化し Set 化して重複検出）で担保する。有効だが、コードが**値**の位置にあるため型では一意性を強制できず、衝突は**テストを実行して初めて**検出される（後追い）。A はこれを静的検出へ前倒しする上位互換。

### C. テストごとにランダムID採番（不採用）

`roleCd` は `VarChar(7)`＝`ROLE`+3桁で**わずか1000通り**しかなく、多数のテストにわたる乱数採番は誕生日問題で現実的に衝突し得る。加えて、flaky 失敗の**再現性**とデータの**可読性**を損ない、実DB検証（ADR-0012）のデバッグ文化と相性が悪い。

### D. ファイル別プレフィックスの明文化（#327・不採用）

#327 は「ユニーク制約列はファイル別プレフィックス必須」をスキルに明文化した。しかし**規律頼み**である本質は変わらず、role/employee 空間では現に破綻していた（本ADRの動機）。

### E. トランザクションでラップしてロールバック（#62案・不採用）

各テストをトランザクション内で実行し終了時にロールバック。ADR-0012 の「実DBの確定的状態に対する検証」と噛み合わず、リポジトリ側のトランザクション制御（atomic submit 等）とも干渉するため見送り。

## 決定

- 共有DB単体テストのコード割当は、**コード空間（ユニークカラム）ごとに1レジストリファイル**を `src/server/__tests__/helpers/test-codes/` に置き、**コードをキー**にした `as const` マップで所有者・用途を宣言する。二重割当は TS1117 でコンパイル時に禁止する（＝承認系のようなランタイム一意性ガードは不要）。
- 消費側は import 時1回構築の派生索引を参照する（逆引きを各テストに書かない）。
- 接頭辞・桁数などの**形式ガード**（および seed 済み正準マスタとの非衝突）は共有ファクトリ `defineTestCodes` で一律に検証する。
- #608 ではまず `roleCd`／`employeeCd` の2空間に適用して flaky を解消する。得意先・商品・納品先ほかの空間は**同じ型で漸進移行**する（#611）。承認系 `approvalTestBands.ts` を本方式へ寄せるかは任意の別スコープ。

## 根拠

- 隔離の不変条件「1コード=1所有ファイル」を、**データ構造そのもの（キーの一意性）＝型検査**で強制する。人間の規律・ランタイム後追い検出のいずれよりも早く・確実に衝突を殺す。
- 有限で小さいコード空間（`roleCd` 1000通り）でも決定的に衝突ゼロを保証でき、失敗の再現性も保つ。

## 影響

- 対象コード空間のテストは、以後コードをハードコードせずレジストリの派生索引から引く。二重割当は `tsc`（pre-push・エディタ）で即エラー。
- 並列 flaky の当該クラス（**書き込み側の一意値衝突**）が構造的に解消する。
- 別クラスの並列 flaky（**読み取り側の広域スキャン競合**＝#90：nested relation の複数SQL間で他テストの削除が刺さり null 化）は本方式の対象外で、クエリ/アサーションのスコープ限定という別解が要る。
- 上位の戦略検討 #62 の採用回答に相当する。旧規律 #327 を「型で強制するレジストリ」へ格上げする。
