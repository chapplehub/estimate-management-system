# ADR-20260709-f2q: dev と e2e の見積・申請 seed フィクスチャを完全分離する（共有をやめ重複を許す）

| 項目 | 値 |
|---|---|
| ステータス | 採用 |
| 起票日 | 2026-07-09 |
| 最終更新日 | 2026-07-09 |

## コンテキスト

#584 / #585 / #589 / #590 で開発・単体テスト・E2E の DB と seed エントリポイント（seed-dev / seed-unit / seed-e2e）は環境別に分離済みだが、見積・申請のフィクスチャ生成モジュール（`seed-estimates.ts` / `seed-estimate-applications.ts`）だけは dev と e2e が共有していた。

#591 で開発環境のデータを大幅拡充する（商品・役割・役割持ち従業員・未申請の見積・多様な申請状態）にあたり、この共有が問題になる。dev と e2e ではフィクスチャに求める性質が逆方向だからである。

- **e2e**: 断定可能性。テストが見積番号（N9905001〜）・従業員コード（EMP000003 等）・役割名に決め打ちで結合し、最小限の決定的データを要求する
- **dev**: 網羅性と現実感。画面で多様なケースを目視でき、承認段階・検索条件・価格帯を横断できる豊富なデータを要求する

共有モジュールには既に双方への妥協が入っている（例: 「dev/e2e 双方で再利用するため特定コードへ結合しない」という制約で FK を findFirst の決定的順序で解決している）。ここに dev の量産データを足すと、E2E の前提を壊すリスクと可読性の劣化が同時に来る。

## 検討した選択肢

### A. 共有ファイルに dev 拡充分を追記する（不採用）

`seed-estimates.ts` / `seed-estimate-applications.ts` に dev 用データを足し、呼び出し側でフラグ分岐する。ファイル数は増えないが、E2E が結合する決定的フィクスチャと dev の網羅データが同居し、「どの行がどちらの前提か」が追えなくなる。dev データの変更が E2E を壊す事故経路が常設される。

### B. dev 専用モジュールを新設しつつ、共有フィクスチャも dev から使い続ける（不採用）

拡充分だけ dev 専用に書き、既存 10 件（全部入り・改訂済み・セット群等）は共有のまま dev でも投入する。追加コストは最小だが、共有部分が残る限り「特定コードへ結合しない」制約は解けず、e2e 側の単純化も dev 側の自由も中途半端になる。分離の判断を先送りするだけで、境界は曖昧なまま残る。

### C. 完全分離: 共有をやめ、dev は自前のフィクスチャを持つ（採用）

dev から `seed-estimates.ts` / `seed-estimate-applications.ts` への import を完全に断ち、両ファイルは e2e 専属とする。dev は `prisma/seed-dev-data/` 配下に自前の見積・申請フィクスチャを新規に持ち、見積番号も dev 専用帯を予約して e2e 予約帯（N9905xxx）と衝突させない。表示多様性（改訂済み・セット群・REPAIR 等）は dev 側の設計に再構成して吸収し、E2E のテスト手順に結合した関心事（トグル用・ボタン出し分け用等）は持ち込まない。

## 決定

dev と e2e の見積・申請フィクスチャを完全分離し、`seed-estimates.ts` / `seed-estimate-applications.ts` は e2e 専属、dev は `prisma/seed-dev-data/` に自前のフィクスチャを持つ。

## 根拠

- dev（網羅性・現実感）と e2e（断定可能性）は最適化の方向が逆であり、共有すると両方が中途半端になる。実際に「特定コードへ結合しない FK 解決」という妥協が既に共有の副作用として入っていた
- 分離により e2e 側は特定コードへの結合を許せるようになり、dev 側は E2E の安定性を人質に取らずデータを自由に育てられる。#584 以降の「環境ごとに seed を分離する」方針の自然な延長でもある
- 見かけ上の DRY 違反（似た Factory＋Mapper 構築コードが 2 系統）は許容する。両者は「同じ知識の重複」ではなく「異なる目的のための別データ」であり、偶発的に似ているにすぎない。無理に共通化すると偽の抽象（フラグ分岐・双方への妥協）が生まれる
- フィクスチャ構築の機構（ドメインの Factory＋Mapper＋seed 専用 PrismaClient で構築し、raw Prisma での金額再実装をしない）は双方で同一方針を維持する。共有しないのはデータ定義であって設計方針ではない

## 影響

- ドメイン（Factory / Mapper のシグネチャ）変更時は dev / e2e 両方の seed の追随が必要になる。単一ファイル修正では済まない
- dev データの拡充・変更が E2E を壊すことはなくなる（逆も同様）。seed 変更 PR のレビュー範囲が「どちらの環境の話か」で明確に切れる
- 一度分離して双方が独自進化した後に再統合するコストは高い。将来「やはり共有したい」となっても、戻すのではなく共通の構築ヘルパーの抽出（データ定義は分離のまま）を検討すること
- dev の見積番号帯は e2e 予約帯（N9905xxx）と分けて管理する。帯の一覧は `prisma/seed-dev-data/README.md` に記録する
