# ADR-20260821-4f1: デプロイ先を公開デモ環境と定義し、初期データ投入に開発 seed を流用する

| 項目 | 値 |
|---|---|
| ステータス | 採用 |
| 起票日 | 2026-08-21 |
| 最終更新日 | 2026-08-21 |

## コンテキスト

Issue #758 でプロダクション用 Docker 構成（`Dockerfile` + `compose.prod.yaml` + Nginx）を整備し、#763 で GHCR へのイメージ push まで通した。しかし初期データ投入の経路が空白のまま残っている（#765）。`migrate` ステージは `prisma migrate deploy` だけを実行するため、**スキーマだけある空 DB の上に app が立ち上がり、誰もログインできず何も登録できない**状態で止まる。

ここで「デプロイ先の DB に何を入れるか」を決める必要がある。この判断はデプロイ先環境の性格そのものの定義と一体であり、後続の EC2 構築イシューを拘束するため、実装に先立って確定させる。

前提となる事実:

- 本リポジトリは**学習目的**であり、デプロイ先で実業務データを扱う予定はない。
- 既存の seed は開発（`prisma/seed-dev.ts`）・単体テスト（`seed-unit.ts`）・E2E（`seed-e2e.ts`）の 3 系統のみで、本番向けは存在しない。
- `seed-dev.ts` は #591 の時点で既に**デモ用途を織り込んで設計されている**（`seed-dev.ts:1222` のコメント「手動確認・デモの入口として提示する」、末尾でログインアカウント一覧を標準出力する作り）。
- Issue #765 が挙げた「初期管理者を作る手段が無い（ニワトリと卵）」は**実際には存在しない**。`seed-dev.ts:4` が `better-auth/crypto` の `hashPassword` を直接 import し、`createUserWithEmployee`（`seed-dev.ts:902-951`）が Employee → User → Account をトランザクションで直接作っている。Better Auth Admin API も管理者セッションも不要。
- 一方で `seed-dev.ts` は seeder ではなく **DB リセットスクリプト**である。冒頭で全テーブルを `deleteMany` し（`seed-dev.ts:1030-1053`）、その後に作り直す。この削除は 1 トランザクションで包まれていない。
- `Dockerfile` の `deps` ステージは `--prod` なしで全依存を入れ、`migrate` ステージがそれを丸ごと受け取っている（実測 972MB）。**`tsx` は migrate イメージに既に入っている**。

## 検討した選択肢

### A. 本番専用 seed を新規に書く（不採用）

正準マスタ（役職・役割・消費税率）＋初期管理者 1 名＋その最小前提行（Department・Employee）だけを upsert で投入する `seed-prod.ts` を新設する。

- 利点: 投入内容が「本番」の意味論に一致する。冪等で非破壊。ダミーの得意先・商品・見積が混入しない。
- 欠点: 4 系統目の seed を恒久的に保守することになり、schema 変更のたびに腐る対象が増える。そして得られるもの（ダミーデータが入らないこと）は**実業務データを持たない環境では価値がない**。むしろ空のアプリはデモとして何も見せられないという欠点だけが残る。

### B. 開発 seed をそのまま流用する（採用）

デプロイ先を公開デモ環境と定義し、`prisma/seed-dev.ts` を当該 DB へ向けて実行する。破壊的な全消し再構築は「デモを初期状態に戻す」操作として仕様に取り込む。

- 利点: 新しい成果物を作らない。2000 従業員・得意先・商品・見積・申請 5 状態まで揃った、デモとして意味のあるデータが即座に入る。冪等性の要求が消える（毎回全消しなので何回叩いても同じ結果）。
- 欠点: デプロイ先の DB を全消しできるスクリプトが公式手順として存在することになる。環境の定義を誤読されると事故に見える。

### C. 条件付き自動実行（不採用）

seed を `migrate` と同じ one-shot に組み込み、「Employee が 0 件なら実行、そうでなければ skip」等のガードで初回だけ走らせる。

- 利点: 初回投入を忘れない。
- 欠点: 判定が外れた瞬間に全消しが走る。さらに開発 seed に「本番かどうか」という概念を持ち込み、開発用スクリプトが本番の都合で挙動分岐する。

## 決定

1. **EC2 上のデプロイ先を「本番」ではなく公開デモ環境と定義する。** 実業務データを置かないこと、ダミーデータが入っていることを欠陥ではなく仕様とする。
2. 初期データ投入は `prisma/seed-dev.ts` をそのまま流用する（選択肢 B）。
3. 実行は**デプロイから分離した明示的な手動 one-shot** とする。`compose.prod.yaml` の profile で `up -d` の対象から除外し、app を停止してから叩き、完了後に再開する。
4. `seed-dev.ts` への改造は**「値の外出し」に限定する**。`SEED_DEFAULT_PASSWORD`（未設定時 `pass123!`）と `SEED_TOTAL_EMPLOYEES`（未設定時 2000）の 2 箇所のみ。挙動分岐は入れない。

## 根拠

- **環境の定義が先に来る。** 「本番」のままでは、全消しスクリプトの流用も 2000 件のダミー従業員も説明不能な事故にしかならない。公開デモと定義した瞬間に、「リセットできること」は欠陥ではなく必要な機能に変わる。この ADR の本体は seed の選択ではなく、この定義そのものである。
- **A の利点は実業務データがある場合にのみ発生する。** 学習目的の環境では、A を選んでも得るものがなく、保守対象が 1 つ増える欠点だけが残る。
- **冪等性・二重実行防止という要求が消滅する。** #765 が未決事項として挙げていた「upsert か skip か」「二重実行をどう防ぐか」は、毎回全消し再構築という性質によって問いごと消える。防止機構を作らないのは手抜きではなく、作る対象が存在しないため。
- **デプロイとリセットを同じ操作に癒着させない**（決定 3）。デプロイ頻度はリセット頻度より高く、自動実行にすると「表示崩れを直して再デプロイしたら入力中のデモデータが消えた」が起きる。これは #761（pull 失敗時に EC2 上ビルドへ暗黙フォールバックする経路）・#762（`depends_on` が効かず app が db より先に起動しうる）と同型の判断で、暗黙に起きる副作用を明示操作へ落とす方向に揃えている。
- **改造の線引き（決定 4）は「挙動分岐か、値の外出しか」で引く。** 挙動分岐は開発 seed に「本番かどうか」という概念を持ち込むため汚染だが、既定値を据え置いたノブは持ち込まない。C を退けたのと同じ基準で、env 2 つは許容される。

## 影響

- **本 ADR の前提（実業務データを置かない）が崩れた時点で、本決定は全面的に無効になる。** デプロイ先を実運用に転じる場合は、seed の切り替えではなく本 ADR の差替（選択肢 A への移行）から入ること。
- デモのログインアカウントは `employee{N}@example.com`（`seed-dev.ts:841`）と規則的で、認証情報は公開される前提。**初回ログイン後のパスワード変更は強制しない**——共有アカウントであり、誰かが変更すると他の人がデモに入れなくなるため。
- `migrate` イメージが migrate と seed の両方を担う。`MIGRATE_IMAGE` という変数名と実態がずれるが、#763 で確定したタグ運用（`latest` = main の写像、`sha-*` はロールバック用）に触れないことを優先し、改名しない。
- EC2 のインスタンスサイズ確定後に `SEED_TOTAL_EMPLOYEES` の調整が要る可能性がある。2000 従業員は `seed-dev.ts:1163-1165` で 1 件ずつ `await` した `$transaction`（3 INSERT）として作られるため、所要時間は件数に線形で、ADR-20260818-7pn が拘束する t4g 系の下位インスタンスでは無視できない長さになりうる。
- `CONTEXT.md` には何も追加しない。「公開デモ環境」はデプロイ環境の語彙であり、見積業務の用語集に属さない。
