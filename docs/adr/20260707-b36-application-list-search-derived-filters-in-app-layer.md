# ADR-20260707-b36: 見積申請一覧の検索は不変事実だけをSQLで絞り、導出条件はアプリ層で畳んでから絞る（limitはフィルタ後適用）

| ステータス | 採用 |

## コンテキスト

#571 で、見積申請一覧画面（/estimate-applications）の読み取りクエリ `SearchEstimateApplications` を実装する。行はバリエーション単位で、対象は「申請または承認免除の記録を持つバリエーション」（＝バリエーション申請状態が NONE 以外）。検索条件は、見積番号・得意先名・納品先名（部分一致）、申請状態（申請中/差戻/取下/承認済/承認不要の複数選択）、申請者名（部分一致）、承認待ち役割（roleId）、申請日（期間）、無効バリエーションを含むかのトグル。表示・検索とも「最新申請（attempt最大の1件）」を出自とする（CONTEXT「最新申請」）。

ここで検索条件が2種類に割れる。

- **不変事実**（attempt に依らず、Estimate/Variation の列やリレーション存在で決まる）: 見積番号・得意先名・納品先名・有効/無効・「申請or免除の記録を持つか」。
- **導出条件**（最新申請スコープで、終端イベント行の存在から導出される）: 申請状態・承認待ち役割・申請者名・申請日時。

申請状態は保存カラムを持たず、承認・差戻・取下イベント行の存在から §3.6 の規則で導出する（ADR-0058）。しかも本一覧は「最新申請のみ」を出自とするため、Prisma のリレーションフィルタ `some`（どれかの attempt にマッチ）では表現できない——過去 attempt にヒットして表示（最新申請の値）と検索が乖離する。したがって導出条件をSQLで絞るには、(1) 相関サブクエリで attempt最大の申請を切り出し、(2) その申請について §3.6 の状態判定を EXISTS/NOT EXISTS で書き直す必要がある。これは「イベント行の存在→状態」という写像（＝ `deriveApplicationStatus` の中身）をSQLで二重実装することを意味し、ADR-0058・ADR-20260706-u7z が一貫して避けてきたドリフト源を、検索文脈で再導入することになる。

「導出条件をSQLで絞ると LIST_FETCH_LIMIT を DB の take で綺麗に効かせられる」対「導出をアプリ層に寄せると単一ソースを保てるが limit を DB で効かせられない」がトレードオフとして衝突したため、方針を確定する。

## 検討した選択肢

### A. 導出条件も相関サブクエリ＋EXISTS/NOT EXISTS でSQL側に寄せ、DBで絞り・take する（不採用）

最新申請を `attempt = (SELECT MAX(attempt) ...)` で切り出し、状態・承認待ち役割を EXISTS/NOT EXISTS で表現、申請者/日時も最新申請へ相関させる。DBで絞り込み＋ `take` が効き、フェッチは常に有界。

不採用理由: §3.6 の状態導出（取下＞差戻＞全承認＞申請中の優先順位、承認待ち＝承認行の無い最小 stepOrder）を `deriveApplicationStatus` とは別にSQLで書き直す。規則がTS関数とSQL文の2箇所に分裂し、将来 §3.6 を変えたとき片方の直し忘れをコンパイラが検出できない。読み取り（一覧の絞り込み）と書き込み（集約getter）で状態の意味がズレる——ADR-0058・u7z が潰したドリフトそのもの。相関サブクエリの複雑さも高い。

### B. 不変事実だけをSQLで絞り、導出条件はアプリ層で畳んでから絞る（採用）

SQLでは不変事実（見積番号・得意先名・納品先名・有効/無効・申請or免除の存在）だけで候補バリエーションを絞る。取得するのは各バリエーションの「終端イベント行の存在有無」という最小射影。そこから先は #559（`PrismaVariationApplicationStateQueryService`）と同じ**書き込みと共有の純粋関数**で畳む:

- 各申請の状態は `deriveApplicationStatus`（§3.6）、
- バリエーション単位は `VariationApplicationState.reduce`（免除最優先→最新attempt→未申請）、
- 承認待ちステップは新設の共有純粋関数 `deriveAwaitingStepOrder`（PENDING 前提で承認行の無い最小 stepOrder）。

還元後の行に対して導出条件（状態・承認待ち役割・申請者名・申請日時）を適用し、申請日時降順→見積番号昇順→バリエーション番号昇順で安定ソートし、先頭 `LIST_FETCH_LIMIT+1` 件を切り出す。免除行の申請者/申請日時は免除者/免除日時を出自とし、検索も一律この出自に効く。

### C. Bに加え、SQLで表現できる導出条件（EXEMPTED・申請者/日時の粗い事前絞り）だけ push down する（不採用）

EXEMPTED は `exemption is not null` で、申請者/日時は「最新がマッチするなら過去 attempt のいずれかもマッチ」ゆえ `some` で偽陰性なく粗く事前絞りできる。これらだけSQLで候補を減らし、残りをアプリ層で確定する。

不採用理由: 状態条件（4値）はSQL化が難しく、結局アプリ層フィルタは残る。粗い事前絞りは分岐と where 構築を増やすだけで、社内見積という有界母数では体感差が出ない（YAGNI）。将来フェッチ量が問題化したらこの最適化を後付けできる（DTO契約は不変のため後戻り可能）。

## 決定

**B を採用する。** 見積申請一覧の検索は、不変事実（Estimate/Variation の列・リレーション存在）だけをSQLの where で絞り、導出条件（最新申請スコープの状態・承認待ち役割・申請者名・申請日時）は、書き込みと共有の純粋関数でアプリ層に畳んでから絞る。`LIST_FETCH_LIMIT` の打ち切りは DB の take ではなくアプリ層のフィルタ・ソート後に適用する。承認待ちステップの導出は共有純粋関数 `deriveAwaitingStepOrder` を新設して単一ソースにする。

## 根拠

- **状態導出を単一ソースに保つ**。§3.6 の写像は `deriveApplicationStatus` の1箇所に集約されており、SQLで絞るとこれを二重実装してドリフトを招く。ADR-0058・u7z の方針を検索文脈でも貫く。#559 が既にアプリ層畳み込みを選んでおり、本クエリはその分業を横展開するだけで一貫する。
- **表示と検索が乖離しない**。最新申請スコープの絞り込みを `some` でSQL化すると過去 attempt にヒットし、一覧に見える申請者名（最新）と検索結果がズレる。アプリ層で還元後の行に絞ればこの乖離が原理的に起きない。
- **非有界フェッチの匂いは有界母数が相殺する**。導出条件をアプリ層に置くと limit を DB で効かせられず、不変事実にマッチする候補を全件取る。だが得意先・見積番号で絞る通常運用では候補は小さく、最悪ケース（状態のみ検索）でも社内見積の業務量は有界。ドリフト回避の利益がこの匂いを上回る。
- **承認待ちも同じ規則の派生**。「承認は stepOrder 順に進む＝承認行の無い最小順序が承認待ち」を読み取りにインライン実装すると §3.6 のステップ導出が書き込み側 `stepStatus` と2箇所に散る。共有純粋関数に切り出して単一ソースにする。

不採用理由:
- **A**: §3.6 のSQL二重実装でドリフトを招き、相関サブクエリも複雑。
- **C**: 状態のアプリ層フィルタは残るのに分岐だけ増える。母数が有界な現状では最適化の価値が無く、必要になれば DTO 契約を変えずに後付けできる。

## 影響

- 検索クエリは不変事実の候補フェッチが**非有界**（DB take を効かせない）。社内見積の有界母数を前提とする。将来フェッチ量が問題化したら、選択肢C（`some` 粗い事前絞り）を DTO 契約を変えずに後付けできる。
- `LIST_FETCH_LIMIT` の意味が「DBが返す件数上限」から「アプリ層フィルタ・ソート後の切り出し件数」に変わる。infra は presentation 定数を import せず、既存クエリ同様 options 経由で受け取る。
- 承認待ちステップ導出の共有純粋関数 `deriveAwaitingStepOrder` が増える（`deriveApplicationStatus` と同じ approval values 配下）。書き込み側 `EstimateApplication.stepStatus` を今回この関数へ委譲リファクタはしない（用途が異なる per-step 分類器のため）。両者は同じ不変条件に依るため、規則変更時は整合を保つ。
- 導出条件で絞る以上、状態と承認待ち役割の矛盾組み合わせ（例: 状態=承認済 かつ 承認待ち役割指定）は AND で素直に空を返す。BE は特別扱いせず、防止は FE の関心。
- DTO 契約（FE が直 type-import・ADR-0069）はフィルタリング方式に依存しないため、本 ADR の内部方式を後で差し替えても FE 影響は無い。
